# Тесты

## Нужен ли тест

Тест нужен для значимых happy path, достижимых крайних случаев и реальных регрессий. Процент покрытия и число тестов не цель. Изменение кода само по себе не требует нового теста.

Перед тем как писать тест, найди существующие проверки, в том числе на более низком уровне, и ответь себе:

- Какое реальное поведение или какой реальный сбой ловит этот сценарий?
- Не покрывает ли его уже другой тест? Что нового найдёт эта проверка?
- На каком самом низком уровне это поведение можно проверить достоверно?

Нет отдельной пользы — не пиши тест, прогони подходящие существующие. Не дублируй через UI тест утилиты или стора, если связка компонентов не добавляет своего риска. Это рабочее решение агента: разрешения на него не спрашивают и отчёт по каждому тесту не пишут.

## Что проверять и чего не проверять

- Проверяй наблюдаемый результат и значимые инварианты нашего кода. Не переписывай реализацию в assertions и не фиксируй внутреннее устройство без причины в поведении.
- Крайний случай должен быть достижим при текущем контракте. Не придумывай невозможные состояния, ветки, которых нет в коде, будущие фичи и сценарии «на всякий случай».
- Опирайся на итоговые требования, а не на историю обсуждения. Если от варианта отказались, не пиши тест, что его нет. Отрицательная проверка нужна только для реального требования или регрессии: отмена не сохраняет правки, пользователь не видит действий администратора.
- Не покрывай косметику: цвета, CSS-классы, отступы, радиусы. Вид проверяют глазами и через Playwright MCP. Исключение — геометрия, от которой зависит работа интерфейса: видимость, перекрытие, прокрутка.
- Не тестируй гарантии библиотек: работу React, Mantine, TanStack Router, Query и Form, zustand, браузерного API. Проверяй нашу логику и её подключение к библиотеке, когда в подключении есть свой риск.
- Правила предметной области (деньги в минимальных единицах, даты без часового пояса, просрочка) проверяй табличными тестами чистых функций, а не через экран.

## Границы тестового файла

Тест лежит рядом с модулем (`foo.tsx` → `foo.test.tsx`) и проверяет сценарии этого модуля. Тест стора или утилиты не монтирует UI ради проверки состояния. Сценарии через роутер и всё приложение лежат в `src/app/`: слои ниже не импортируют `test-router`. Страница проверяется в своём слайсе.

Бери минимум зависимостей, нужный сценарию. Сначала используй существующие хелперы, не раздувай setup и моки ради простой проверки. Дополняй подходящую группу сценариев, если она остаётся сфокусированной; несвязанные сценарии в один файл не складывай.

Тексты `describe` и `it` пишутся по-русски и описывают поведение: «Escape закрывает диалог без действия», а не «вызывает onClose».

## Прогоны

Из `frontend/`:

```bash
pnpm exec vitest run <путь>   # тесты, относящиеся к изменению
pnpm exec eslint <пути>       # точечный линт изменённых файлов, без --quiet
pnpm typecheck                # vitest типы не проверяет: зелёный тест может не компилироваться
pnpm lint:fsd                 # если менялись импорты между слайсами или структура слайса
pnpm check                    # перед сообщением о готовности: типы, линтеры, формат, тесты, сборка
```

Предупреждения линтера в своих строках разбирай, а не пропускай. Среди них бывают предупреждения React Compiler.

## Поиск элементов

- Элемент с понятной пользователю подписью ищи так же, как пользователь: `getByRole(роль, { name })`, поле формы — `getByLabelText`. Так запрос заодно проверяет, что у элемента есть роль и подпись.
- `data-testid` — только там, где роли и подписи нет и не должно быть: контейнер, область прокрутки. Имя описывает назначение, а не вид или позицию.
- Не выбирай элемент по номеру в списке (`getAllByRole(...)[1]`): соседний элемент незаметно подменит цель.
- Нет подписи у нового контрола — добавь её (`aria-label` у `ActionIcon`), а не testid. Роли и aria-атрибуты, не нужные пользователю, ради теста не навешивай.
- Существующие `data-testid` не удаляй и не переименовывай без согласования с пользователем.

## Хелперы

| Что | Где |
|---|---|
| Рендер компонента в теме Mantine | `renderWithTheme(ui)` из `@shared/lib/test-utils` |
| Страница или виджет с запросами | `renderWithQuery(ui)` из `@shared/lib/test-utils`: `renderWithTheme` и свежий `QueryClient` без повторов, возвращает и `queryClient`; ответы API - через `apiServer.use(handleXxx(...))`, профиль для `useCurrentUser` - через `signIn(role)` |
| Приложение целиком на адресе | `renderApp(path)` из `src/app/test-router.tsx`: роутер с настройками приложения (`appRouterOptions`) и тестовым клиентом запросов |
| Ширина окна и тема системы | `stubMatchMedia({ width, colorScheme })` из `@shared/lib/test-utils`: `matchMedia` отвечает на `min-width`, `max-width` и `prefers-color-scheme`; вызывай до рендера |
| Ответы API | `apiServer.use(handleXxx(...))` из `@shared/lib/test-utils`: MSW-сервер; обработчики `handleXxx` для каждой операции контракта экспортирует тот же модуль (тело ответа или функция `({ request }) => HttpResponse`). Запрос без описанного ответа роняет тест |
| Ошибка API | `apiErrorResponse(status, code, headers?)` - ответ для `handleXxx(...)` в формате Aéza v2 (`handleLogin(apiErrorResponse(400, 'invalid_credentials'))`); `apiErrorBody(status, code)` - само тело |
| Вход через форму | `serveSignInFlow({ role, requirements })`: ответы входа, обмена challenge, кода 2FA и профиля; возвращает `{ email }`. `serveCurrentUserForToken(token)` - `GET /auth/me` принимает только этот токен, на остальные `401 not_auth`, возвращает массив присланных заголовков |
| Время и участники | `hoursFromNow(hours)` - момент в формате API (отрицательное - в прошлом), `accountEmail(role)` - email тестового участника |
| Сегодня сервера | `serveSettings({ today, reminderDaysBefore })` из `@shared/lib/test-utils`: ответ `GET /settings`, по умолчанию 24.10.2026 и окно 3 дня. Экраны со сроками без него не загрузятся |
| Экран «Платежи» | `servePaymentsScreen({ occurrences, totals, departments })` из `@shared/lib/test-utils`: настройки, периоды, итоги и отделы; без аргументов - пустой экран. Нужен каждому тесту через `renderApp`, который попадает на `/payments` (туда ведёт вход). `currencyTotals({ currency, ... })` - итоги валюты с нулями по умолчанию |
| Раздел «Регулярные платежи» | `serveRecurringScreen({ payments, occurrences, departments })` из `@shared/lib/test-utils`: настройки, отделы, список платежей с фильтрами `status` и `departmentId` по страницам, карточка платежа (неизвестный id - 404) и его периоды от новых к старым. Массив `payments` читается на каждый запрос: тест может добавить или изменить платёж в ответ на запись |
| Вход с ролью | `signIn(role)` из `@shared/lib/test-utils`: сессия на 12 часов и ответ `GET /auth/me` для `admin`, `user` или `integration`; вызывай до `renderApp`, возвращает `{ email }` |

Новый общий хелпер добавляй в эту таблицу.

`vitest.setup.ts` поднимает ожидание `findBy` и `waitFor` до 3 секунд (холодный рендер приложения при параллельном прогоне), подменяет браузерные API, которых нет в jsdom (`matchMedia`, `ResizeObserver`, `scrollIntoView`, `scrollTo`), запускает MSW-сервер и подключает клиент API к сессии, а после каждого теста возвращает настоящие таймеры, размонтирует компоненты, убирает уведомления Mantine, сбрасывает ответы API и сессию, чистит `localStorage` и `sessionStorage`. `unstubGlobals: true` снимает `vi.stubGlobal`, `mockReset: true` перед каждым тестом сбрасывает все моки и шпионы. Свои `afterEach` и `mockReset()` для этого не заводи.

## Известные грабли

- **Mantine в тестах рендерится с `env="test"`:** это делают `renderWithTheme` и `renderApp`. Анимации выключены, а `Modal`, `Popover`, `Menu` и уведомления рисуются без портала, на месте. Свой `MantineProvider` в тесте не заводи.
- **React Compiler работает и в тестах:** `vite.config.ts` подключает его для Vitest тоже. Компонент без изменившихся пропсов отдаёт запомненную разметку:
  - мок хука с данными делай реактивным — состояние в сторе zustand, тест меняет его через `act(() => store.setState(…))`; обычный объект, изменённый перед `rerender`, не сработает;
  - обёртка без пропсов (`Harness`) тоже запоминается, поэтому `rerender(<Harness />)` ничего не меняет.
- **`renderApp` берёт клиент запросов приложения** (`createQueryClient({ test: true })`): повторов после ошибки нет, ошибка видна сразу.
- **Окружение — jsdom:** раскладки нет, размеры элементов нулевые. Геометрию и прокрутку проверяй в браузере через Playwright MCP, а не в unit-тесте.
- **Неактивная кнопка с `pointer-events: none`:** `userEvent.click` бросает ошибку. Если сценарий проверяет, что нажатие ничего не делает, используй `userEvent.setup({ pointerEventsCheck: 0 })`.
- **Файл вне `src`, например `index.html`, читай импортом `?raw`:** `import html from '../../index.html?raw'`.
- **`getByText` и неразрывные пробелы:** текст элемента нормализуется (`\u00a0` становится обычным пробелом), а строка запроса - нет. В `getByText` пиши обычные пробелы; доступные имена (`getByRole(..., { name })`) не нормализуются, там нужен `\u00a0`.
- **Значение по умолчанию у параметра:** `fn(undefined)` проваливается в дефолт. Для «нет данных» передавай `null`.
- **Моки сбрасываются перед каждым тестом (`mockReset: true`):** `vi.fn()` снова возвращает `undefined`, `vi.fn(impl)` возвращается к `impl`, шпион `vi.spyOn` — к настоящей функции. Ответы, нужные всем тестам файла, задавай в `beforeEach`, а не на уровне модуля; `…Once` — только если тест гарантированно делает этот вызов.
