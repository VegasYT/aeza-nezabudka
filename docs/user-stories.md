# User stories Invoice Keeper

## Роли

- **Пользователь** — просматривает общие платежи и управляет оплатой отдельных периодов.
- **Администратор** — обладает возможностями пользователя, управляет регулярными платежами и пользователями. Учётная запись администратора задаётся в `.env` и через панель не меняется.

## Аутентификация и доступ

### US-01. Вход в систему

**Как** пользователь,  
**я хочу** входить в Invoice Keeper своим аккаунтом Aéza,  
**чтобы** получать безопасный доступ к функциям, разрешённым моей роли.

**Приоритет:** высокий.

**Критерии приёмки:**

- Неаутентифицированный пользователь видит форму входа: email и пароль аккаунта Aéza, при включённой 2FA - второй шаг с кодом.
- После успешного входа пользователь получает доступ к веб-панели.
- Войти может только аккаунт из белого списка; остальные после верного пароля видят сообщение "нет доступа, обратитесь к администратору".
- Роль определяется белым списком системы, а не аккаунтом Aéza.
- После нескольких неудачных попыток вход временно ограничивается.
- При недействительном или истёкшем токене система требует повторного входа.
- Без входа данные недоступны: API отвечает 401 на любой запрос без корректного токена.
- Веб-панель получает email и роль текущего пользователя через `GET /api/v1/auth/me`.

### US-14. Выход из системы

**Как** пользователь,  
**я хочу** выйти из Invoice Keeper,  
**чтобы** никто другой не работал от моего имени на этом устройстве.

**Приоритет:** средний.

**Критерии приёмки:**

- После выхода сессия завершена на сервере, веб-панель показывает форму входа.
- После выхода прежний токен не действует.

### US-02. Ограничение административных операций

**Как** администратор,  
**я хочу** быть единственным пользователем, который может управлять регулярными платежами,  
**чтобы** исключить несанкционированные изменения общего списка.

**Приоритет:** высокий.

**Критерии приёмки:**

- Создание, изменение и прекращение регулярных платежей, а также управление пользователями доступны только администратору.
- Обычный пользователь не видит административные действия в интерфейсе.
- При прямом запросе обычного пользователя к административной операции API возвращает отказ в доступе.
- Ограничения применяются независимо от того, выполнено действие через интерфейс или напрямую через API.

## Просмотр платежей

### US-03. Просмотр общего списка

**Как** пользователь,  
**я хочу** видеть общий список регулярных платежей,  
**чтобы** понимать текущие обязательства компании.

**Приоритет:** высокий.

**Критерии приёмки:**

- Список доступен всем аутентифицированным пользователям.
- Для каждого платежа отображаются основные сведения, валюта и ближайший срок.
- После изменения данных список показывает актуальное состояние.

### US-04. Просмотр платёжных периодов

**Как** пользователь,  
**я хочу** просматривать ежемесячные периоды регулярного платежа,  
**чтобы** видеть срок и состояние оплаты каждого месяца отдельно.

**Приоритет:** высокий.

**Критерии приёмки:**

- Для каждого месяца существует отдельный платёжный период.
- У периода отображаются название платежа, сумма, валюта, срок, статус оплаты и просрочка.
- Оплата одного периода не изменяет статусы других периодов.
- Если период оплачен, отображается фактическая дата оплаты.

### US-15. Появление следующего периода

**Как** пользователь,  
**я хочу**, чтобы следующий период платежа появлялся сам,  
**чтобы** видеть ближайшее обязательство, не дожидаясь действий администратора.

**Приоритет:** высокий.

**Критерии приёмки:**

- У действующего платежа всегда виден ближайший будущий период со своим статусом "Не оплачено".
- Следующий период появляется независимо от того, оплачен ли предыдущий: просрочка не останавливает следующие периоды.
- Прошлые периоды и их отметки об оплате сохраняются.
- Если система была выключена, после запуска появляются все пропущенные периоды, каждый ровно один раз.
- Если в месяце нет числа срока (например, 31-го), срок переносится на последний день месяца; следующий срок снова считается от исходного числа.

### US-05. Просмотр итогов по валютам

**Как** пользователь,  
**я хочу** видеть суммы платежей отдельно по каждой валюте,  
**чтобы** оценивать обязательства без искажения из-за неявной конвертации.

**Приоритет:** средний.

**Критерии приёмки:**

- Система показывает отдельные итоги для RUB, USD и EUR.
- Суммы в разных валютах не складываются между собой.
- Система не выполняет конвертацию валют.

### US-06. Просмотр просрочек

**Как** пользователь,  
**я хочу** видеть просроченные платёжные периоды,  
**чтобы** своевременно реагировать на неоплаченные обязательства.

**Приоритет:** высокий.

**Критерии приёмки:**

- Неоплаченный период не считается просроченным в день наступления срока.
- Неоплаченный период считается просроченным начиная со следующего дня после срока.
- После отметки оплаты период больше не отображается как неоплаченная просрочка.
- Оплата в день срока считается своевременной; оплата позже срока отображается как оплата с просрочкой.
- Просрочка определяется автоматически по сроку, отметке и фактической дате, без ручных действий.

## Управление регулярными платежами

### US-07. Создание регулярного платежа

**Как** администратор,  
**я хочу** добавлять регулярные платежи,  
**чтобы** команда могла отслеживать новые обязательства.

**Приоритет:** высокий.

**Критерии приёмки:**

- Администратор может заполнить обязательные сведения о платеже.
- Для платежа можно выбрать валюту RUB, USD или EUR.
- Обязательные сведения: название, сумма, валюта, дата ближайшей оплаты, периодичность (ежемесячно).
- Дата ближайшей оплаты не может быть раньше сегодняшней.
- После сохранения платёж появляется в общем списке.
- Система создаёт периоды платежа по US-15.
- Если до срока 3 дня или меньше, напоминание отправляется сразу, не дожидаясь плановой проверки.
- При некорректных или неполных данных система не создаёт платёж и сообщает об ошибках.

### US-08. Изменение регулярного платежа

**Как** администратор,  
**я хочу** изменять сведения и сроки регулярного платежа,  
**чтобы** поддерживать список обязательств в актуальном состоянии.

**Приоритет:** высокий.

**Критерии приёмки:**

- Администратор может открыть существующий платёж для редактирования.
- Можно изменить название, сумму, валюту и дату ближайшей оплаты.
- Изменение действует только на неоплаченные периоды со сроком сегодня или позже. Оплаченные и просроченные периоды не меняются: история остаётся прежней.
- Новое название отображается у всех периодов платежа.
- При смене даты будущие неоплаченные периоды пересчитываются от новой даты; новая дата не может быть раньше сегодняшней.
- Если новый срок попадает в ближайшие 3 дня, напоминание по нему отправляется сразу.
- Прекращённый платёж изменить нельзя.
- После сохранения новые сведения отображаются в общем списке.
- При некорректных данных система сохраняет прежнее состояние и сообщает об ошибках.

### US-09. Прекращение регулярного платежа

**Как** администратор,  
**я хочу** прекращать больше не актуальные регулярные платежи,  
**чтобы** они не учитывались среди действующих обязательств.

**Приоритет:** средний.

**Критерии приёмки:**

- Перед прекращением система запрашивает подтверждение.
- После подтверждения платёж исчезает из списка действующих платежей.
- История сохраняется: прошлые и оплаченные периоды остаются в списке с пометкой "платёж прекращён".
- Будущие неоплаченные периоды удаляются.
- Для прекращённого платежа больше не отправляются напоминания, в том числе уже запланированные.

## Управление оплатой

### US-10. Отметка периода оплаченным

**Как** пользователь,  
**я хочу** отметить конкретный период оплаченным и указать фактическую дату,  
**чтобы** команда видела актуальное состояние обязательства.

**Приоритет:** высокий.

**Критерии приёмки:**

- Пользователь выбирает конкретный платёжный период.
- При отметке оплаты сохраняется фактическая дата платежа.
- Период отображается как оплаченный сразу после успешного сохранения.
- Статусы остальных периодов не изменяются.

### US-11. Исправление даты оплаты

**Как** пользователь,  
**я хочу** исправить фактическую дату оплаты периода,  
**чтобы** устранить ошибку в истории платежей.

**Приоритет:** средний.

**Критерии приёмки:**

- Дату можно изменить только у периода, отмеченного оплаченным.
- После сохранения отображается исправленная дата.
- Статус периода остаётся оплаченным.
- Просрочка пересчитывается по новой дате: если новая дата не позже срока, ошибочная просрочка исчезает.
- Срок оплаты периода при этом не меняется.
- Фактическая дата не может быть позже сегодняшней.

### US-12. Отмена отметки об оплате

**Как** пользователь,  
**я хочу** отменить ошибочную отметку об оплате,  
**чтобы** вернуть периоду фактический статус.

**Приоритет:** средний.

**Критерии приёмки:**

- Пользователь может отменить отметку у оплаченного периода.
- После отмены период отображается неоплаченным.
- Фактическая дата оплаты очищается.
- Если срок уже прошёл, период отображается просроченным.

## Напоминания

### US-13. Получение напоминания о приближающемся платеже

**Как** пользователь,  
**я хочу** получать напоминание в общем Telegram-чате заранее,  
**чтобы** бухгалтерия успевала оплатить обязательство до наступления срока.

**Приоритет:** высокий.

**Критерии приёмки:**

- Система регулярно проверяет сроки неоплаченных периодов.
- Напоминание отправляется, когда до срока осталось 3 дня или меньше, но срок ещё не прошёл.
- Платёж, добавленный позже чем за 3 дня до срока, получает напоминание сразу.
- Напоминание содержит название, сумму, валюту и дату оплаты.
- По одному периоду в общий чат отправляется одно напоминание, даже при повторной проверке, перезапуске системы или нескольких параллельных проверках.
- Для оплаченного периода и прекращённого платежа напоминание не отправляется, даже если оно уже было запланировано.
- Если Telegram временно недоступен, отправка повторяется позже; напоминание не теряется.
- В первый день просрочки неоплаченного периода приходит одно напоминание о просрочке.
- Общий чат задаётся в настройках системы (`.env`).

### US-18. Личные напоминания в Telegram

Telegram служит только для уведомлений: привязка личного чата не даёт прав, никаких действий через бота (ADR-010).

**Как** пользователь,  
**я хочу** по своему выбору получать напоминания в личный чат с ботом,  
**чтобы** не пропустить срок, даже если не слежу за общим чатом.

**Приоритет:** средний.

**Критерии приёмки:**

- В веб-панели пользователь нажимает "Подключить Telegram" и получает ссылку на бота; после запуска бота по этой ссылке личный чат привязан к его учётной записи.
- Ссылка одноразовая и действует 10 минут; по старой или чужой ссылке бот ничего не привязывает и подсказывает, что делать.
- Пользователь включает и выключает личные напоминания, не отвязывая Telegram.
- Пользователь может отвязать Telegram в панели или командой `/stop` в боте.
- Личные напоминания приходят по тем же правилам, что и в общий чат (US-13): окно 3 дня, состав сообщения, одно напоминание на период каждому получателю.
- Общий чат и личные чаты независимы: выключение личных напоминаний не влияет на общий чат.
- Если пользователь выключил личные напоминания или отвязал Telegram, уже запланированные личные напоминания ему не отправляются.
- Если пользователь заблокировал бота, система перестаёт ставить ему напоминания, а панель объясняет, как снова запустить бота.
- Удалённый пользователь личных напоминаний не получает.

## Управление пользователями

### US-16. Управление пользователями

**Как** администратор,  
**я хочу** давать и забирать доступ к системе,  
**чтобы** доступ к платежам был только у нужных людей.

**Приоритет:** высокий.

**Критерии приёмки:**

- Администратор видит список участников.
- Администратор добавляет email аккаунта Aéza с ролью "Пользователь" или "Интеграция"; человек сразу может войти своим аккаунтом Aéza. Паролей в системе нет.
- Администратор меняет роль участника, отключает и включает его.
- Администратор удаляет участника; история отметок оплаты сохраняется с его email, привязка Telegram удаляется.
- Отключённый или удалённый участник теряет доступ сразу, его сессии завершаются.
- Через панель и API нельзя назначить роль администратора.
- Обычный пользователь не может выполнить ни одну из этих операций, в том числе напрямую через API.

### US-17. Администратор из настроек

**Как** владелец системы,  
**я хочу** задавать администраторов в `.env`,  
**чтобы** система никогда не осталась без управляющего.

**Приоритет:** высокий.

**Критерии приёмки:**

- Администраторы - email аккаунтов Aéza из `ADMIN_EMAILS` в `.env`; пароль хранит Aéza.
- Администратор может войти сразу после первого запуска.
- Администратора нельзя изменить или удалить через панель и API.
- После смены `ADMIN_EMAILS` и перезапуска действует новый список; убранный email теряет доступ.

## Отделы

### US-19. Отделы

**Как** администратор,  
**я хочу** относить платежи к отделам,  
**чтобы** бухгалтерия видела расходы по направлениям.

**Приоритет:** средний.

**Критерии приёмки:**

- Администратор создаёт, переименовывает и удаляет отделы.
- У платежа можно указать отдел или оставить его без отдела.
- В списке периодов и в итогах по валютам можно выбрать отдел.
- После удаления отдела его платежи остаются и становятся "без отдела".
- Отдел не влияет на права: все пользователи видят все платежи.

## Встраивание

### US-20. Интеграция с системами компании

**Как** администратор системы у заказчика,  
**я хочу** подключить Invoice Keeper к другим системам компании,  
**чтобы** платежи и оплаты не приходилось вести в двух местах.

**Приоритет:** средний.

**Критерии приёмки:**

- Внешняя система работает с платежами через API с ключом `X-API-KEY` своего аккаунта Aéza, добавленного администратором с ролью "Интеграция", и не может управлять участниками и отделами.
- Повтор запроса на создание с тем же ключом идемпотентности не создаёт платёж второй раз.
- О создании, изменении и прекращении платежа, приближении срока, оплате, отмене оплаты и просрочке система сообщает событием на webhook и в Kafka, если они настроены.
- Webhook подписан, и получатель может проверить подпись.
- Повтор события получатель распознаёт по его идентификатору.
- Без настроенных интеграций система работает как обычно; сбой webhook или Kafka не мешает напоминаниям.

## Технические требования

Эти пункты являются требованиями к реализации, а не самостоятельными user stories:

- REST API имеет базовый путь `/api/v1`. Пути могут отличаться от таблиц кейса; соответствие описано в [plan.md](plan.md), раздел 7.
- Все данные сохраняются после перезапуска системы.
- Контракт API описан в OpenAPI.
- Для API доступна документация Swagger.
- Проверка аутентификации и ролей выполняется на стороне API, а не только в интерфейсе.
- Секреты и реальные учётные данные не хранятся в репозитории.
