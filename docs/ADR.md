## ADR-001: монорепо и запуск через Docker Compose

- **Статус:** предложено

### Контекст

Кейс требует веб-панель, API со Swagger, Telegram-бота и запуск жюри по README. Решение сдаётся одним комплектом: код, инструкция, `.env.example`, тестовые данные.

По уточнениям к кейсу ([Case.md](Case.md)): система ставится on-premise у одной компании, multi-tenancy не нужен; нагрузка у уведомлений небольшая; систему стоит проектировать так, чтобы она встраивалась в инфраструктуру заказчика.

### Решение

Один репозиторий: `backend/`, `frontend/`, `infra/`. Всё решение поднимается одной командой Docker Compose: PostgreSQL, backend, Caddy со статикой frontend. Проверка сроков и отправка напоминаний - процесс `worker` из того же кода и образа backend, а не отдельный сервис со своим кодом (ADR-013).

Caddy - единственная точка входа: `/api` ведёт в backend, остальное - статика frontend. Всё на одном домене. Вход проверяет API Aéza (ADR-014), в compose его нет.

Одна установка - одна компания: арендаторов, изоляции данных между компаниями и выбора компании нет.

Не используем: микросервисы, брокер сообщений внутри системы, Redis и event sourcing. При небольшой нагрузке они добавляют только точки отказа. Kafka появляется лишь как необязательный канал интеграции с брокером заказчика (ADR-011).

### Последствия

- жюри запускает решение одной командой;
- нет межсервисного взаимодействия и распределённых сбоев;
- CORS не нужен;
- фоновая задача и API делят одну базу; при нескольких экземплярах backend отправку защищает очередь в базе (ADR-004).

## ADR-002: OpenAPI-контракт как источник истины

- **Статус:** принято, изменено ADR-013 и ADR-015 (2026-10-24)

### Контекст

Кейс требует OpenAPI-спецификацию в `.yml` или `.json` и рабочий Swagger на `/api/v1/docs`. Frontend и backend пишутся параллельно.

### Решение

Контракт лежит в `backend/api/openapi.yaml`. Он выгружается из приложения FastAPI: источник истины - схемы Pydantic и роутеры, файл - их проверяемая копия. Тест падает, если файл не совпадает с тем, что строит приложение. Типы клиента frontend генерируются из файла.

Первоначальный вариант "файл пишется руками раньше кода" заменён при выборе FastAPI (ADR-013).

### Последствия

- приложенная спецификация не расходится с реализацией: это проверяет тест;
- правка контракта затрагивает обе части и делается через OpenSpec change; после правки схем файл выгружается заново и коммитится.

## ADR-003: регулярный платёж и период оплаты - разные сущности

- **Статус:** предложено

### Контекст

У каждого периода своя дата, отметка оплаты и фактическая дата. Новый период не стирает прошлые оплаты, просрочка не останавливает следующие периоды, удалённый платёж сохраняет историю.

### Решение

- **Регулярный платёж** (`recurring_payment`): название, сумма, валюта, периодичность, якорный день, действующее расписание (`schedule_first_due_date`, `schedule_from_seq`), признак прекращения.
- **Период** (`payment_occurrence`): ссылка на платёж, номер, срок оплаты, копия суммы и валюты, фактическая дата оплаты (`paid_on`). Статус "Оплачено" - это `paid_on is not null`, отдельного поля статуса нет.
- Периоды создаются заранее. Инвариант: у активного платежа есть все периоды со сроком до сегодня и ровно один будущий. Следующий период появляется независимо от оплаты предыдущего. `unique (платёж, номер)` делает досоздание безопасным при повторе.
- Удаление платежа - мягкое (прекращение): платёж помечается прекращённым, прошлые и оплаченные периоды остаются, будущие неоплаченные периоды удаляются вместе с их ожидающими напоминаниями.
- Изменение платежа меняет только неоплаченные периоды со сроком сегодня или позже. Смена даты начинает новый отрезок расписания с номера после последнего оставшегося периода. Оплаченные и просроченные периоды не меняются.
- Срок месячного периода считается от якорного дня. Если такого числа в месяце нет, берётся последний день месяца. Следующий срок считается снова от якорного дня, а не от прошлого срока: после 28 февраля идёт 31 марта, а не 28 марта.

### Последствия

- история оплат и просрочек хранится явно и не переписывается задним числом;
- состояние "оплачено без даты" невозможно по устройству модели;
- нужна фоновая задача, которая досоздаёт следующие периоды;
- другие периодичности добавляются функцией расчёта следующего срока.

## ADR-004: напоминания через очередь в базе (outbox)

- **Статус:** предложено

### Контекст

Напоминание уходит минимум за 3 дня до срока, без дублей. Оплаченный период и прекращённый платёж напоминаний не получают. Платёж, добавленный позже чем за 3 дня до срока, получает напоминание сразу. Схема "проверил, что не отправлено, отправил, записал" даёт дубль при двух параллельных запусках.

### Решение

Таблица `notifications` с `unique (период, тип, канал, получатель)` и два независимых шага. Получатель - общий чат или конкретный пользователь (ADR-010).

- **Постановка.** Раз в минуту, а также в транзакции создания или изменения платежа, один запрос вставляет напоминания для периодов в окне: не оплачен, платёж не прекращён, `сегодня <= срок <= сегодня + 3`. Строка ставится для общего чата и для каждого пользователя с включёнными личными напоминаниями. `on conflict do nothing`: второе напоминание по периоду тому же получателю база не создаст.
- **Отправка.** Ожидающие строки берутся через `for update skip locked`. Перед отправкой условия проверяются заново: оплаченный период, прекращённый платёж, выключенные личные напоминания или отвязанный Telegram отменяют напоминание. Временная ошибка Telegram - повтор с растущей паузой, окончательная (чат не найден) - состояние `failed` с причиной.
- Отменили оплату после напоминания - второе не отправляется: одно напоминание на период каждому получателю.
- Кроме напоминания до срока (`kind = due_soon`) есть одно напоминание о просрочке (`kind = overdue`): в первый день просрочки неоплаченного периода действующего платежа. Защита от дублей та же.
- Новые каналы (email, webhook) - новое значение канала, механизм тот же.

### Последствия

- дубль невозможен при повторных тиках, перезапуске и нескольких экземплярах backend: это гарантирует база, а не код;
- при падении процесса между ответом Telegram и коммитом возможен один повтор. Это допустимо: потерять напоминание хуже, чем отправить его дважды;
- история отправок и ошибок видна в таблице.

## ADR-005: администратор задаётся через `.env`

- **Статус:** заменено ADR-014 (2026-10-24): администраторы задаются списком email аккаунтов Aéza в `ADMIN_EMAILS`, пароль хранит Aéza

### Контекст

Кейс требует администратора из `.env`, которого нельзя изменить через панель. Пользователей создаёт администратор.

### Решение

- Пользователи хранятся в Keycloak (ADR-008). При каждом старте backend синхронизирует администратора через Admin API Keycloak: создаёт пользователя `ADMIN_LOGIN` при отсутствии, ставит пароль `ADMIN_PASSWORD`, роль `admin` и атрибут `env_managed=true`. Если логин в `.env` сменили, прежний администратор отключается и теряет роль.
- Через API учётная запись с ролью `admin` не меняется и не удаляется (409), роль `admin` не назначается.
- Обычных пользователей администратор создаёт, меняет и удаляет через `/api/v1/users` - фасад над Admin API Keycloak.
- Роль проверяется на сервере для каждой операции. Скрытая кнопка во frontend защитой не считается.

### Последствия

- смена пароля администратора - правка `.env` и перезапуск;
- система не остаётся без администратора;
- критерий "пользователь не выполнит действия администратора даже через API" проверяется тестами API.

## ADR-006: даты без времени и единый часовой пояс

- **Статус:** предложено

### Контекст

Просрочка начинается со следующего дня после срока, оплата в день срока - вовремя. Часовой пояс единый, задаётся в настройках или `.env`.

### Решение

- Срок оплаты и фактическая дата оплаты хранятся как даты без времени.
- "Сегодня" считается в часовом поясе из `.env` (`TZ`, имя IANA, например `Europe/Moscow`).
- Просрочка не хранится, а вычисляется: период не оплачен и сегодня позже срока, либо оплачен и фактическая дата позже срока.

### Последствия

- исправление фактической даты сразу пересчитывает просрочку, срок не меняется;
- нет ошибок на границе суток из-за UTC.

## ADR-007: суммы в минимальных единицах валюты

- **Статус:** предложено

### Контекст

Три валюты, итоги считаются отдельно по каждой, конвертации нет.

### Решение

Сумма хранится целым числом в минимальных единицах (копейки, центы) вместе с кодом валюты `RUB`, `USD` или `EUR`. Итоги группируются по валюте и никогда не складываются между валютами.

### Последствия

- нет ошибок округления дробных чисел;
- API и интерфейс явно переводят минимальные единицы в отображаемую сумму.

## ADR-008: вход через Keycloak по OIDC

- **Статус:** заменено ADR-014 (2026-10-24): вход через аккаунты Aéza вместо своей базы пользователей
- **Дата:** 2026-10-23

### Контекст

Кейс требует вход по логину и паролю и защиту панели и API. Инструмент выбирает команда, а пути эндпоинтов не обязаны совпадать с кейсом ([Case.md](Case.md), уточнения). Рассматривались: своя авторизация на сессиях, Keycloak с передачей пароля через backend (Direct Access Grants), Keycloak со стандартным входом из браузера.

### Решение

- Keycloak - источник истины для пользователей, паролей и ролей (`admin`, `user`). Данные Keycloak хранятся в отдельной базе того же PostgreSQL.
- Вход - OIDC Authorization Code + PKCE через страницу Keycloak. Frontend - публичный клиент, токены держит только в памяти и обновляет сам. Выход - завершение сессии в Keycloak.
- Backend - сервер ресурсов: проверяет `Bearer`-токен локально по ключам JWKS (подпись, `iss`, `aud`, срок) и берёт роль из токена. `GET /api/v1/auth/me` отдаёт логин и роль.
- Keycloak опубликован через Caddy на том же домене по пути `/auth`, чтобы `iss` совпадал у браузера и backend. Консоль администратора наружу закрыта.
- Swagger входит через Keycloak (OAuth2 Authorization Code + PKCE).
- Access token живёт 5 минут. Смена пароля, отключение и удаление пользователя через API завершают его сессии в Keycloak.

Direct Access Grants отклонён: приложение видело бы пароль, способ устарел в OAuth 2.1, а 2FA и SSO становились бы недоступны. Своя авторизация отклонена командой в пользу готового решения.

### Последствия

- пароль видит только Keycloak; защита от перебора, политика паролей и журнал входов готовы без кода; 2FA и SSO включаются настройкой;
- `POST /auth/login` и `POST /auth/logout` из кейса заменены входом и выходом Keycloak; соответствие эндпоинтам - в [plan.md](plan.md), раздел 7;
- тяжёлый контейнер: около 0,5-1 ГБ памяти и старт до минуты; README об этом предупреждает;
- уже выданный access token действует до 5 минут после отключения пользователя;
- если Keycloak недоступен, войти нельзя, но выданные токены работают до истечения.

## ADR-009: метрики и централизованные логи в Grafana

- **Статус:** принято, изменено 2026-10-24 (Grafana на поддомене с паролем)
- **Дата:** 2026-10-23

### Контекст

Для демонстрации и эксплуатации нужно видеть состояние API, фоновых задач и отправки напоминаний, а также искать логи всех контейнеров в одном интерфейсе. Одного вывода `docker compose logs` недостаточно: он не показывает динамику показателей и неудобен для сопоставления событий разных компонентов.

Prometheus хранит метрики, но не логи. Promtail собирает и пересылает логи, но не хранит их и не является источником данных Grafana. Поэтому для централизованных логов нужен Loki.

### Решение

- **Prometheus** опрашивает внутренний endpoint backend `/metrics`. Endpoint не публикуется через Caddy и доступен только внутри сети Docker Compose.
- Backend отдаёт технические и бизнес-метрики: количество и длительность HTTP-запросов по маршруту, методу и коду ответа; результаты тиков планировщика; размер и возраст очереди outbox; результаты и повторы отправки уведомлений; ошибки работы с PostgreSQL, API Aéza и Telegram.
- В метках метрик запрещены идентификаторы платежей, пользователей, URL с конкретными ID и тексты ошибок. Это ограничивает кардинальность и не допускает попадания персональных данных.
- Все контейнеры пишут структурированные JSON-логи в `stdout`/`stderr`. Запись содержит время, уровень, компонент, сообщение и `request_id` либо идентификатор фоновой операции. Пароли, Bearer-токены, токен Telegram-бота и другие секреты не журналируются.
- **Promtail** читает логи контейнеров Docker, добавляет только ограниченный набор меток (`service`, `environment`, `level`) и отправляет записи в **Loki**.
- **Loki** запускается в однопроцессном режиме и хранит логи в отдельном именованном томе с ограниченным сроком хранения. Он доступен только во внутренней сети Compose.
- **Grafana** получает метрики из Prometheus, а логи из Loki. Оба источника данных и стартовый dashboard provisioning-настраиваются из файлов репозитория, без ручных действий после запуска.
- Стартовый dashboard показывает доступность backend, частоту и длительность запросов, долю ошибок, состояние планировщика, размер и возраст outbox, результаты отправки в Telegram. Из панелей можно перейти к логам того же сервиса и временного интервала.
- Grafana является эксплуатационным интерфейсом, а не частью пользовательской веб-панели. Она открыта на поддомене `grafana.<домен>` через Caddy с HTTPS и закрыта паролем администратора из `.env`; регистрация и анонимный вход выключены. Изменено 2026-10-24: на защите Grafana показывают по ссылке, без SSH-туннеля. Prometheus и Loki наружу по-прежнему не открываются.

Promtail достиг конца жизненного цикла 2 марта 2026 года и больше не получает обновлений. Он используется по решению команды с закреплённой версией. Конфигурация сбора логов изолируется в отдельном файле без Promtail-специфичных допущений в приложении, чтобы затем заменить агент на Grafana Alloy.

### Последствия

- метрики и логи доступны в одном интерфейсе Grafana;
- для логов добавляется обязательный компонент Loki, а для Prometheus, Loki и Grafana нужны отдельные именованные тома;
- Compose становится тяжелее и требует лимитов ресурсов и хранения;
- нужно контролировать кардинальность метрик, объём логов и срок хранения;
- отказ стека наблюдаемости не должен останавливать API, планировщик и отправку напоминаний;
- Promtail создаёт технический долг: после хакатона его нужно заменить поддерживаемым агентом, предпочтительно Grafana Alloy.

## ADR-010: напоминания в общий чат и в личные чаты

- **Статус:** принято
- **Дата:** 2026-10-24
- **Изменено:** 2026-10-24 - администратор подключает дополнительные групповые чаты с фильтром отделов
- **Изменено:** 2026-10-25 - темы супергрупп, оформленные сообщения с кнопками, отметка оплаты и "напомнить завтра" из Telegram

### Контекст

Кейс требует напоминания в указанный Telegram-чат. Сценарий из уточнений к кейсу: бухгалтерия компании забывает оплачивать регулярные счета ([Case.md](Case.md), уточнения). Команда решила, что сотруднику может быть удобнее получать напоминания лично, а общий чат при этом остаётся. Telegram не даёт боту написать человеку первым: пользователь должен сам запустить бота.

Сначала Telegram был только каналом доставки: по уточнению к кейсу пользователь Telegram не связан с учётной записью. 2026-10-25 решение пересмотрено: нужно больше работы прямо в Telegram - темы супергрупп, оформленные сообщения и кнопки под ними. Человека, нажавшего кнопку, система узнаёт по личной привязке, которую он сам сделал из панели; без привязки кнопки ничего не меняют.

Ветка А утверждена. Ветка Б, в которой личными получателями управляет администратор без связи с учётными записями, отклонена: она усложняет администрирование и лишает пользователя самостоятельного управления личными уведомлениями, не добавляя прав через Telegram.

### Решение

- Два независимых канала. Общий чат задаётся в `.env` (`TELEGRAM_CHAT_ID`) и получает все напоминания. Личный чат каждый пользователь подключает сам и сам включает или выключает личные напоминания.
- Привязка по одноразовому коду: панель выдаёт ссылку `t.me/<бот>?start=<код>`, бот получает `/start <код>` и связывает `chat_id` с пользователем. Код живёт 10 минут, используется один раз, в базе хранится его хеш.
- Обновления бота backend читает long polling (`getUpdates`), без публичного webhook. Опрос ведёт один экземпляр backend под advisory-блокировкой PostgreSQL: Telegram разрешает один `getUpdates` на токен.
- В личный чат приходят напоминания обо всех платежах: список общий. Пользователь может оставить только платежи выбранных отделов (ADR-012).
- Ответ Telegram "бот заблокирован пользователем" отмечается в привязке, и этому пользователю напоминания больше не ставятся, пока он снова не запустит бота.
- Удаление пользователя удаляет его привязку.
- **Групповые чаты.** Кроме общего чата из `.env`, администратор подключает другие группы, например чат отдела. Панель выдаёт ссылку `t.me/<бот>?startgroup=<код>`: Telegram предлагает выбрать группу, добавляет туда бота и присылает в неё `/start <код>`. У чата фильтр отделов: все платежи или только платежи выбранных отделов (платежи без отдела туда не идут). Напоминания ставятся по тем же правилам, что и общему чату; паузы те же. Если бота удалили из группы, чат помечается заблокированным сразу по обновлению `my_chat_member` (и по ошибке отправки) до повторного подключения; переименование группы обновляет название чата. Общий чат из `.env` остаётся и получает всё. Управляет чатами только администратор (`/api/v1/telegram-chats`).
- **Темы супергрупп.** Одну группу можно подключить к нескольким темам, у каждой подключения свой фильтр отделов. Панель выдаёт одноразовый код в двух видах: ссылка `startgroup` добавляет бота в группу (сообщения без темы), команда `/start@<бот> <код>`, отправленная в теме группы, где бот уже есть, подключает эту тему. В группе с темами код, пришедший в "Общее" (туда его всегда шлёт ссылка), сразу ничего не подключает: бот отвечает командой для нужной темы, а "Общее" подключается повтором команды там же. Иначе после подключения темы напоминания шли бы дважды. Бот запоминает тему и её название; удаление бота из группы и переименование группы касаются всех её тем. Для общего чата из `.env` тема задаётся `TELEGRAM_THREAD_ID`.
- **Оформление.** Сообщения в HTML с эмодзи статуса: скоро срок, просрочено, новый платёж, оплачено. Под напоминанием кнопки "Оплачено", "Напомнить завтра" и ссылка "Открыть в панели" (`PUBLIC_URL`). Когда период оплатили - в панели или кнопкой - бот правит уже отправленные сообщения: "Оплачено", кто и когда, кнопки убираются.
- **Действия из Telegram - только две и только безопасные:** отметить период оплаченным сегодняшней датой и отложить напоминание этого чата на завтра. Нажавший должен быть участником с личной привязкой (его Telegram id - id личного чата в привязке), включённым и не интеграцией; иначе бот отвечает подсказкой привязать Telegram в панели. Кнопка проверяется по сообщению, к которому она приложена: данные кнопки чужого сообщения не подходят. Отметка пишется в журнал действий от имени участника с пометкой "через Telegram". Отмена оплаты, исправление даты и изменение платежа - только в панели.
- О новом платеже бот пишет в общий и групповые чаты (с учётом фильтра отделов).

### Последствия

- общий чат по сценарию кейса работает как раньше; личные напоминания - надстройка, их можно выключить;
- нагрузка на Telegram растёт с числом получателей; паузы ведутся по чатам, поэтому один чат не задерживает другие;
- в личном чате видны суммы и сроки, поэтому привязать чат может только вошедший пользователь и только к собственной учётной записи;
- Telegram-аккаунт с личной привязкой может отметить оплату и отложить напоминание; кто получил доступ к Telegram участника, сможет сделать то же, поэтому остальные действия остаются только в панели, а смена роли на интеграцию снимает привязку;
- сообщения нужно править после оплаты, поэтому id отправленного сообщения хранится в очереди напоминаний.

## ADR-011: встраивание в инфраструктуру заказчика

- **Статус:** принято
- **Дата:** 2026-10-24

### Контекст

Уточнения к кейсу: "Больше думайте в сторону что это куда-то встраивается или может быть встроено" и "наличие того же MQ может повернуть решение". Система ставится on-premise. У заказчика уже есть свои системы (учётная система, каталог сотрудников) и, возможно, свой брокер сообщений. В списке дополнительных возможностей кейса есть webhook и другие каналы.

### Решение

**События наружу.** Изменения в системе публикуются как интеграционные события через транзакционный outbox:

- типы: `payment.created`, `payment.updated`, `payment.stopped`, `occurrence.due_soon`, `occurrence.paid`, `occurrence.unpaid`, `occurrence.overdue`;
- событие записывается в той же транзакции, что и изменение, поэтому не теряется и не появляется без изменения;
- у события есть `id` (ключ идемпотентности для получателя), тип, версия схемы, время и данные;
- `occurrence.due_soon` и `occurrence.overdue` ставит планировщик; уникальный ключ события не даёт выпустить их дважды;
- доставка - адаптерами за одним интерфейсом, у каждого адаптера своё состояние доставки и повторы.

Адаптеры:

- **webhook** - HTTP POST на адрес из `.env`, подпись HMAC-SHA256 общим секретом, повторы с растущей паузой;
- **Kafka** - публикация в топик брокера заказчика, адрес из `.env`; ключ сообщения - идентификатор платежа, чтобы события одного платежа шли по порядку.

RabbitMQ и другие брокеры не реализуем. Если у заказчика другой брокер, добавляется ещё одна реализация того же интерфейса, ядро не меняется. В нашем compose Kafka есть только в профиле `integration`: она изображает брокер заказчика для демо.

**Входящее встраивание.**

- API `/api/v1` с OpenAPI-контрактом.
- Другие системы заказчика (например, 1С) ходят в API с заголовком `X-API-KEY` - ключом своего аккаунта Aéza; аккаунт добавлен в белый список с ролью `integration` (ADR-014): создание и изменение платежей, отметка оплаты. Пользователями управлять эта роль не может.
- `POST` принимает заголовок `Idempotency-Key`: повтор запроса с тем же ключом возвращает прежний результат и не создаёт платёж дважды.
- Сотрудники входят аккаунтами Aéza (ADR-014). Вход через Active Directory или LDAP, который давал Keycloak, отпал вместе с ним.

### Последствия

- ядро не зависит от интеграций: без настроенных адаптеров события копятся только как журнал и никуда не уходят; сбой webhook или брокера не мешает напоминаниям в Telegram;
- на защите на вопрос "зачем Kafka" есть ответ: это брокер заказчика, а не часть нашей архитектуры;
- появляется контракт событий; его версия меняется так же осторожно, как версия API;
- в compose для демо добавляется профиль `integration` с Kafka; по умолчанию он выключен и не утяжеляет запуск у жюри.

## ADR-012: отделы как слабо связанная фича

- **Статус:** принято
- **Дата:** 2026-10-24

### Контекст

Команда решила сделать отделы: в бухгалтерии компании платежи удобно делить по отделам или направлениям. Уточнение к кейсу: отделы "как доп. фича - да, вполне. В идеале чтобы система на этом сильно не завязывалась" ([Case.md](Case.md), уточнения).

### Решение

- Справочник отделов ведёт администратор: создание, переименование, удаление.
- У регулярного платежа необязательная ссылка на отдел. При удалении отдела ссылка очищается, платежи остаются.
- Отдел - только для группировки и фильтров: фильтр в списке периодов, итоги по валютам с фильтром по отделу, отдел в напоминаниях и интеграционных событиях. Групповому чату и получателю личных напоминаний можно ограничить отделы (ADR-010). Если все отделы из такого фильтра удалили, получатель снова получает напоминания по всем платежам: лишнее напоминание лучше пропущенного. Название отдела уникально без учёта регистра.
- Права от отделов не зависят: администраторов отделов и ограничения видимости по отделу нет. Все пользователи видят все платежи, как требует кейс.

### Последствия

- платёж без отдела работает как раньше; отключить фичу - значит не заводить отделы;
- в ядре одна необязательная ссылка и один фильтр, правила сроков, просрочки и напоминаний не меняются;
- права по отделам при необходимости добавляются отдельным решением, но это уже изменение модели доступа.

## ADR-013: backend на FastAPI с модулями в `apps/`

- **Статус:** принято
- **Дата:** 2026-10-24

### Контекст

Команда выбрала стек backend: FastAPI и модульную архитектуру с папкой `apps/`. Нужно закрепить границы модулей, инструменты, способ запуска фоновых задач и совместить FastAPI с ADR-002 (контракт OpenAPI).

### Решение

**Стек.** Python 3.12, весь ввод-вывод асинхронный:

- FastAPI, Pydantic v2, pydantic-settings;
- PostgreSQL через SQLAlchemy 2 (async) и asyncpg, миграции Alembic;
- httpx для клиента API Aéza: вход и проверка `X-API-KEY` (ADR-014);
- aiogram для Telegram; прокси задаётся `TELEGRAM_PROXY_URL` (`socks5://` или `http://`, через aiohttp-socks), чтобы обойти блокировки Telegram;
- httpx для webhook, aiokafka для адаптера Kafka;
- structlog для JSON-логов, prometheus-client для `/metrics` (ADR-009);
- uv, ruff (линтер и форматирование), mypy, import-linter для границ модулей, pytest с pytest-asyncio и testcontainers.

**Модули.** Модульный монолит: каждая предметная область - модуль в `backend/apps/` (`payments`, `reminders`, `users`, `departments`, `integrations`, `audit`). Общее - в `backend/core/`. Модуль обращается к другому только через его сервис, `core/` не зависит от `apps/`; правило проверяет import-linter. Структура модуля - в [backend/AGENTS.md](../backend/AGENTS.md).

**Два процесса из одного кода.** Один образ, два запуска:

- `api` - FastAPI (uvicorn): HTTP, Swagger на `/api/v1/docs`, `/metrics`, health;
- `worker` - фоновые задачи: досоздание периодов, постановка и отправка напоминаний, чтение обновлений бота, доставка интеграционных событий; свой `/healthz` и `/metrics`.

Медленный Telegram, прокси или Kafka не задевают время ответа API, а при нескольких процессах uvicorn планировщик не размножается. Защита от двойной работы всё равно в базе (ADR-004), поэтому второй `worker` ничего не ломает; чтение обновлений бота держит advisory-блокировку.

**Контракт выгружается из кода.** Схемы пишутся на Pydantic, `backend/api/openapi.yaml` выгружается командой из приложения и коммитится, тест падает, если файл устарел. Frontend генерирует типы из этого файла. Чтобы frontend мог начать раньше, backend на первом шаге пишет роутеры и схемы с заглушками.

**Тестовые данные** загружаются отдельной командой, а не флагом при старте.

Альтернатива для контракта - писать `openapi.yaml` руками и генерировать из него модели Pydantic. Отклонена: два источника правды, которые приходится сверять, и это против обычного способа работы FastAPI.

### Последствия

- ADR-002 изменён: источник истины - схемы Pydantic, файл - их проверяемая копия;
- в compose два сервиса backend из одного образа;
- для асинхронного кода тесты тоже асинхронные, интеграционные тесты поднимают PostgreSQL и Kafka в контейнерах, API Aéza заменяет фейк;
- без `TELEGRAM_PROXY_URL` бот ходит в Telegram напрямую.

## ADR-014: вход через аккаунты Aéza и белый список

- **Статус:** принято
- **Дата:** 2026-10-24
- **Заменяет:** ADR-005, ADR-008
- **Изменено:** ADR-015 - шаги и формат входа как у Aéza (`use-challenge`, `tfa/totp`)

### Контекст

Уточнение к кейсу (2026-10-24): своя база пользователей не нужна, если вход идёт через Aéza и на нём показан весь сценарий ([Case.md](Case.md), уточнения).

У Aéza (`https://my.aeza.ru/api`, проверено на тестовом аккаунте хакатона) вход в два шага:

1. `POST /api/v2/auth/login` с email и паролем возвращает одноразовый `challenge` и `requirements` - список дополнительных проверок (пусто - 2FA не нужна);
2. `POST /api/v2/auth/use-challenge` (или `auth/tfa/totp` с кодом 2FA) меняет `challenge` на сессию примерно на 30 дней.

Сессия передаётся как `Authorization: Bearer`, ключ из кабинета ("API ключи") - как `X-API-KEY`; `GET /api/v2/accounts/me` возвращает id, email и данные аккаунта. Сессия и ключ дают полный доступ к аккаунту хостинга: заказ, оплату и удаление серверов. Аккаунт Aéza есть у любого клиента хостинга, а система ставится у одной компании.

### Решение

- **Пароли хранит только Aéza.** Keycloak, своих паролей и регистрации нет.
- **Белый список.** Таблица `members`: email аккаунта Aéza, роль (`admin`, `user`, `integration`), id аккаунта Aéza (привязывается при первом входе, дальше вход сверяется по нему), включён ли участник. Администраторы - email из `ADMIN_EMAILS` в `.env`: `api` синхронизирует их при старте, через API они не меняются и не удаляются (409), а email, убранный из списка, теряет доступ вместе с сессиями. Остальных участников добавляет администратор через `/api/v1/users`. Аккаунт Aéza не из списка после верного пароля получает 403.
- **Вход сотрудника.** Панель отправляет email и пароль в `POST /api/v1/auth/login`. Backend проходит вход Aéza: при пустом `requirements` - сразу `use-challenge`, иначе отвечает "нужен код 2FA", и панель отправляет код в `POST /api/v1/auth/tfa`. Получив сессию Aéza, backend узнаёт аккаунт через `accounts/me`, сразу закрывает сессию Aéza (`auth/logout`), находит участника в списке и выдаёт свою сессию. Пароль не сохраняется и не попадает в журнал.
- **Своя сессия.** Случайный токен, в базе только его хеш, срок `SESSION_TTL_HOURS` (по умолчанию 12 часов), передаётся как `Authorization: Bearer`. Проверка - запрос в свою базу, без обращения к Aéza. Выход, отключение и удаление участника удаляют его сессии сразу.
- **Другие системы** (например, 1С) передают `X-API-KEY` - ключ своего аккаунта Aéza. Backend проверяет ключ через `accounts/me` и запоминает результат на 60 секунд по хешу ключа; аккаунт должен быть в белом списке, обычно с ролью `integration`. Ключ не пишется ни в базу, ни в журнал.
- **Перебор паролей.** Все входы уходят в Aéza с одного адреса - нашего сервера, а у WAF Aéza есть бан IP за неудачные входы (применяется ли он к их входу и какой у него порог, неизвестно). Поэтому backend считает неудачные входы сам: не больше 5 за 10 минут на email и на IP клиента, и не больше 20 за 10 минут на весь сервер; дальше 429 без обращения к Aéza. Общий предел на время блокирует вход всем, но короче и предсказуемее бана IP у Aéza. Попросить Aéza внести IP сервера в исключения WAF или назвать порог.
- **Адрес API Aéza** - `AEZA_API_URL`, по умолчанию `https://my.aeza.ru/api`. Клиент Aéza - за интерфейсом `IdentityProvider`, в тестах его заменяет фейк.
- **Вход для разработки** (2026-10-24). С `DEV_LOGIN_PASSWORD` email на `@dev.local` входят по этому паролю без Aéza, с кодом 2FA `000000` для email с `+2fa` и ключами `dev:<email>:<пароль>`; challenge подписан паролем, чтобы его нельзя было собрать из email. Остальные email по-прежнему проверяет Aéza, поэтому тестовые и настоящие аккаунты работают одновременно. Белый список, роли, сессии и лимиты общие. Это нужно для работы над frontend без тестового аккаунта и без 429 от Aéza. При `APP_ENV=production` настройка запрещена: с общим паролем в публичную панель вошёл бы любой, кто знает email из списка.
- В Swagger две схемы: `bearer` (токен из `POST /auth/login`) и `X-API-KEY`.
- `POST /auth/login` и `POST /auth/logout` снова совпадают с путями кейса.

Отклонено:

- пускать любой аккаунт Aéza: в данные компании попал бы любой клиент хостинга; показывать каждому только его платежи - это мультитенантность, которую система не поддерживает ([plan.md](plan.md), раздел 1);
- отдавать браузеру сессию Aéza и проверять её на каждом запросе: токен с правами на хостинг жил бы в нашем frontend, а каждый запрос зависел бы от Aéza;
- оставить Keycloak и подключить Aéza как внешний провайдер: Aéza не даёт OIDC, понадобился бы свой адаптер вдобавок к тяжёлому контейнеру.

### Последствия

- в compose нет Keycloak: запуск легче и быстрее, `infra/keycloak` удаляется;
- войти нельзя, пока API Aéza недоступен; уже выданные сессии работают без него, ключи `X-API-KEY` - до конца 60 секунд кеша;
- 2FA, сброс пароля и политика паролей - на стороне Aéza, своего кода для них нет;
- вход через Active Directory или LDAP (ADR-011) больше не предусмотрен;
- `X-API-KEY` даёт полный доступ к аккаунту Aéza, поэтому для интеграции заводится отдельный аккаунт; наш backend ключ не хранит;
- на человека в таблицах ссылаемся по id участника из `members`, email копируется в историю, как раньше логин;
- если Aéza включит капчу на входе, проксирование входа сломается: нужен будет виджет капчи в панели и передача `X-Captcha-Token`.

## ADR-015: контракт API в стиле Aéza v2

- **Статус:** принято
- **Дата:** 2026-10-24
- **Изменяет:** ADR-002 (соглашения формата), ADR-014 (шаги входа)

### Контекст

Сервис встраивается в инфраструктуру Aéza, вход идёт через их аккаунты (ADR-014). Команда решила, что весь наш API должен выглядеть как API Aéza v2, чтобы им было привычно с ним работать. Frontend пока готов только как дизайн-система, поэтому менять контракт ещё дёшево.

Соглашения Aéza v2 сняты с живого API (`https://my.aeza.ru/api/v2`, 2026-10-24):

- поля в camelCase (`expiresAt`, `paymentTerm`), даты и время - ISO 8601 с `Z`, суммы - целое число в минимальных единицах (`price`);
- список - `{items, total}`, параметры `limit` и `offset`;
- ошибка - `{statusCode, message, error, timestamp, path, payload, requestId}`: `error` - код для программы (`not_auth`, `not_found`, `invalid_credentials`), `payload` - подробности;
- ошибка проверки данных - 400, `payload` - список `[{field, message}]`; не найдено - 404 `not_found`, `payload` - `{entity, id}`; нет авторизации - 401 `not_auth`;
- вход - `POST /auth/login` (`{challenge, requirements}`), затем `POST /auth/use-challenge` или `POST /auth/tfa/totp` (`{session, expiresAt}`), выход - `POST /auth/logout` (204).

### Решение

Наш API `/api/v1` следует этим соглашениям:

- JSON тел запросов, ответов и параметров запроса - camelCase; в коде Python имена остаются snake_case, перевод делают схемы Pydantic.
- Список - `{items, total}` с параметрами `limit` (1-100, по умолчанию 50) и `offset`.
- Ошибка - `{statusCode, message, error, timestamp, path, payload, requestId}`. `message` - на русском (его показывает панель), `error` - код, `requestId` совпадает с заголовком `X-Request-ID`.
- Ошибки проверки данных - 400 `bad_request` со списком полей в `payload` (вместо 422 с `fields`); не найдено - 404 `not_found` с `{entity, id}`; без авторизации - 401 `not_auth`.
- Вход повторяет шаги Aéza: `POST /auth/login` возвращает `challenge` и `requirements` (их выдаёт Aéza), `POST /auth/use-challenge` и `POST /auth/tfa/totp` - `{session, expiresAt}`, где `session` - токен нашей сессии.
- Интеграционные события (ADR-011) тоже в camelCase.

Остаются как были: префикс `/api/v1`, пути эндпоинтов кейса (`/recurring-payments`, `/payment-occurrences`, `/auth/me` и другие), идентификаторы UUID, заголовки `Authorization`, `X-API-KEY` и `Idempotency-Key`.

Отклонено: копировать API Aéza целиком, включая их пути и целочисленные id, - это ломает эндпоинты кейса, а у самой Aéza форматы v1 и v2 различаются; брать формат v1 (`{error: {slug, message, data}}`) - v2 новее, и именно его использует их кабинет.

### Последствия

- клиент, умеющий работать с API Aéza v2, разбирает наши ответы и ошибки тем же кодом;
- меняется весь контракт: имена полей, формат ошибок, код 422 становится 400; frontend пишется сразу под новый контракт;
- спецификации OpenSpec описывают поля по именам в коде (snake_case), в контракте они в camelCase;
- `message` на русском отличается от английских сообщений Aéza: панель показывает его пользователю.
