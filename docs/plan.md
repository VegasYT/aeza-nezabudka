# План разработки

Кейс: [Case.md](Case.md). Архитектурные решения: [ADR.md](ADR.md).

Цель архитектуры - чтобы каждый критерий приёмки держался на гарантии базы данных или чистой функции с тестом, а не на аккуратности кода. Жюри проверяет корректность: дубли напоминаний, права через API, просрочку, сохранение после перезапуска. Поэтому надёжность закладывается в модель данных, а не добавляется потом.

Система ставится on-premise у одной компании, нагрузка небольшая, а встраиваемость в инфраструктуру заказчика важна (уточнения к кейсу в [Case.md](Case.md)). Поэтому не делаем: multi-tenancy, микросервисы, брокер сообщений внутри системы, Redis и event sourcing. Kafka есть только как необязательный канал интеграции с брокером заказчика (ADR-011).

## 1. Общая схема

```text
                         браузер
               (frontend: форма входа,
                запросы к API с Bearer-токеном)
                            |
                       [ Caddy ]  HTTPS, статика frontend,
                            |     /api -> backend
                            |
   +------------------------+-------+         [ API Aéza ]  my.aeza.ru/api
   | backend: api + worker          |              ^       пароли, 2FA,
   |                                |              |       аккаунты
   |  HTTP API /api/v1 --> сервисы  |--------------+  вход (challenge),
   |    Swagger         --> домен   |                 проверка X-API-KEY
   |    /metrics        <-----------+---------------- [ Prometheus ]
   |  планировщик (тик 1 мин)       |                         ^
   |   - досоздание периодов        |
   |   - постановка напоминаний     |
   |  отправитель outbox -----------+------> Telegram Bot API
   +----------+---------------------+
              |
       [ PostgreSQL ]  платежи, периоды, outbox, журнал,
                       белый список и сессии

   [ Grafana ] -- PromQL --> [ Prometheus ]
       |
       +------ LogQL -----> [ Loki ] <----- push ----- [ Promtail ]
                                                            ^
                                                            | JSON stdout/stderr
                              backend, Caddy, PostgreSQL и другие контейнеры
```

- **Backend - один код, два процесса** (ADR-013). `api` обслуживает HTTP, `worker` выполняет планировщик, отправку напоминаний, чтение обновлений бота и доставку интеграционных событий. Процессы не делят состояние в памяти: всё общее лежит в PostgreSQL. Поэтому второй экземпляр любого из них ничего не ломает (раздел 6).
- **PostgreSQL** - источник истины для платежей, периодов, outbox и журнала. Ограничения базы (`unique`, `check`, внешние ключи) защищают инварианты даже при ошибке в коде.
- **Вход через аккаунты Aéza** (ADR-014). Пароли и 2FA хранит Aéza, backend проходит её вход и выдаёт свою сессию. Кто может войти и с какой ролью, решает белый список в нашей базе (раздел 5).
- **Caddy** раздаёт собранный frontend и проксирует `/api` в backend. Всё на одном домене, CORS не нужен.
- **Наблюдаемость.** Prometheus собирает метрики backend, Promtail отправляет логи контейнеров в Loki, Grafana показывает оба источника. Сбой этого контура не влияет на основные сценарии приложения (ADR-009).
- **Встраивание.** Интеграционные события уходят из outbox через адаптеры: webhook и Kafka заказчика. Другие системы ходят в API с `X-API-KEY` своего аккаунта Aéza из белого списка. Без настроенных адаптеров ядро работает как обычно (раздел 7, ADR-011).

## 2. Слои backend

| Слой | Что делает | Чего не делает |
| --- | --- | --- |
| HTTP | разбор запроса по контракту, коды ответов, проверка токена | бизнес-правила |
| Сервисы | сценарии: транзакция, проверка роли, запись в журнал | SQL-строки в коде сценария, даты "на глаз" |
| Домен | чистые функции: расчёт сроков, просрочка, окно напоминания, деньги | ввод-вывод, текущее время |
| Хранилище | SQL, транзакции, блокировки | решения |
| Интеграции | API Aéza за интерфейсом `IdentityProvider`, Telegram за интерфейсом `Notifier`, webhook и Kafka за интерфейсом `EventPublisher` | знание о платежах |

- Слои ложатся на модули FastAPI в `backend/apps/` (ADR-013): `router.py` - HTTP, `service.py` - сценарии, `domain.py` - домен, `repository.py` и `models.py` - хранилище. Общее (настройки, база, `Clock`, проверка токена) - в `backend/core/`. Подробно - [backend/AGENTS.md](../backend/AGENTS.md), шаги реализации - [backend/plan.md](../backend/plan.md).
- `IdentityProvider`: вход в Aéza (challenge, 2FA) и проверка `X-API-KEY` через `accounts/me` (httpx). Реализации две: клиент API Aéza и фейк для тестов. Адрес - `AEZA_API_URL`.
- `Notifier`: отправка в Telegram через aiogram, при необходимости через прокси (`TELEGRAM_PROXY_URL`, SOCKS5 или HTTP), потому что Telegram в РФ может быть заблокирован.
- Время приходит через интерфейс `Clock`. В тестах подставляется фиксированная дата, в демо можно задать дату через переменную окружения (только вне продакшена). Без этого сценарии "просрочка" и "следующий период" нельзя проверить быстро.

## 3. Модель данных

Все суммы - целые минимальные единицы (ADR-007), даты срока и оплаты - `date` без времени (ADR-006). Паролей в базе приложения нет, их хранит Aéza. На человека ссылаются по id участника из `members`, а его email копируется рядом, чтобы история читалась и после удаления участника.

### recurring_payments

`id`, `name`, `amount_minor` (check > 0), `currency` (`RUB` | `USD` | `EUR`, check), `period` (`day` | `week` | `month` | `year`), `period_count` (каждые N единиц, 1-366), `anchor_day` (1-31), `schedule_first_due_date`, `schedule_from_seq`, `department_id` (fk, null - без отдела, on delete set null), `stopped_at` (null - активен), `created_by_id`, `created_by_login`, `created_at`, `updated_at`.

- `schedule_first_due_date` и `schedule_from_seq` задают действующее расписание: с какого номера периода и с какой даты оно считается. При создании `schedule_from_seq = 0`. Изменение расписания начинает новый отрезок, не трогая прошлые периоды (раздел 4).

### payment_occurrences

`id`, `recurring_payment_id` (fk), `seq` (номер периода с 0), `due_date`, `amount_minor`, `currency`, `paid_on` (null - не оплачено), `paid_by_id`, `paid_by_login`, `updated_at`.

- `unique (recurring_payment_id, seq)`: повторное досоздание периода ничего не дублирует.
- Статус - это `paid_on is not null`. Отдельного поля статуса нет, поэтому состояние "оплачено без даты" или "не оплачено с датой" невозможно. Отмена оплаты обнуляет `paid_on`, как требует кейс.
- Сумма и валюта копируются в период при создании. История не поменяется, даже если позже появится редактирование платежа.
- Просрочка не хранится, а считается из `due_date`, `paid_on` и "сегодня" (раздел 4).

### notifications (outbox)

`id`, `occurrence_id` (fk), `kind` (`due_soon` - до срока, `overdue` - первый день просрочки), `channel` (`telegram`), `recipient` (`group` - общий чат или id участника - личный чат), `state` (`pending` | `sent` | `cancelled` | `failed`), `attempts`, `next_attempt_at`, `last_error`, `sent_at`, `external_id` (id сообщения в Telegram).

- `unique (occurrence_id, kind, channel, recipient)`: два одинаковых напоминания об одном периоде одному получателю база не допустит. Это главный механизм "без дублей".
- В строке хранится получатель, а не номер чата: чат берётся при отправке. Если пользователь перепривязал Telegram, напоминание уйдёт в новый чат.

### telegram_links

`user_id` (pk, id участника из `members`), `login` (email), `chat_id` (unique), `telegram_username`, `personal_enabled` (bool), `linked_at`, `blocked_at` (null - бот может писать).

- Связь пользователя системы с его личным чатом с ботом. Бот не может написать человеку первым: пользователь должен сам открыть бота (раздел 6).
- `personal_enabled` - выбор пользователя: получать ли напоминания в личный чат. Отключить можно без отвязки.
- `blocked_at` ставится, если Telegram ответил, что пользователь заблокировал бота. Такой пользователь не получает напоминаний, пока снова не запустит бота.

### telegram_link_codes

`code_hash` (pk), `user_id`, `expires_at`, `used_at`.

- Одноразовый код привязки, живёт 10 минут. В базе только хеш кода.

### departments

`id`, `name` (unique), `created_at`.

- Справочник отделов (ADR-012). Только группировка и фильтры: права от отделов не зависят.

### integration_events (outbox интеграций)

`id` (uuid, он же ключ идемпотентности для получателя), `type`, `schema_version`, `dedup_key` (unique), `payload` (jsonb), `created_at`.

- Пишется в той же транзакции, что и изменение (ADR-011).
- `dedup_key` не даёт выпустить событие дважды: например, `occurrence.overdue:<id периода>` планировщик пытается поставить на каждом тике, но запишется оно один раз.

### integration_deliveries

`event_id` (fk), `target` (`webhook` | `kafka`), `state` (`pending` | `sent` | `failed`), `attempts`, `next_attempt_at`, `last_error`, `sent_at`.

- `unique (event_id, target)`. Строки создаются только для включённых адаптеров. Отправка - тем же способом, что и напоминания: `for update skip locked`, повторы с паузой.
- Отправленные события старше срока хранения удаляются раз в сутки.

### idempotency_keys

`key`, `actor_id`, `operation`, `request_hash`, `response` (jsonb), `created_at`.

- `unique (actor_id, key)`. Повтор `POST` с тем же ключом и тем же телом возвращает сохранённый ответ, с другим телом - 422. Ключи старше суток удаляются.

### members (белый список)

`id` (uuid), `email` (unique, в нижнем регистре), `aeza_account_id` (unique, null до первого входа), `role` (`admin` | `user` | `integration`), `source` (`env` | `panel`), `enabled`, `created_at`, `last_login_at`.

- Кто может войти и с какой ролью (ADR-014). Аккаунт Aéza не из списка получает 403.
- При первом входе `aeza_account_id` привязывается, дальше участник находится по нему: смена email в Aéza доступ не ломает.
- Строки `source = env` создаёт синхронизация `ADMIN_EMAILS`, через API они не меняются.

### sessions

`token_hash` (pk, sha256 токена), `member_id` (fk, `on delete cascade`), `created_at`, `expires_at`.

- Своя сессия после входа через Aéza. Токен в базе не хранится, только хеш.
- Выход удаляет строку, отключение участника удаляет все его сессии. Истёкшие удаляет задача `worker` раз в час.

### login_failures

`scope` (`email:<email>`, `ip:<адрес>` или `server`), `failed_at`; индекс `(scope, failed_at)`.

- Счётчик неудачных входов для пределов из раздела 5: сколько строк за последние 10 минут. Общий для всех экземпляров `api`.
- Строки старше суток удаляет задача `worker`.

### audit_log

`id`, `at`, `actor_id`, `actor_login`, `action`, `entity`, `entity_id`, `details` (jsonb).

- Пишется в той же транзакции, что и действие. Операции с участниками, входы и выходы тоже попадают в журнал. Закрывает дополнительную возможность "Логи" почти бесплатно.
- Изменение платежа пишет в `details` старые и новые значения.

## 4. Правила предметной области

Все правила - чистые функции домена с табличными тестами.

### Расчёт срока

- `due(seq) = clamp(anchor_day, месяц(schedule_first_due_date) + (seq - schedule_from_seq))`, где `clamp` берёт последний день месяца, если такого числа нет.
- Срок всегда считается от якорного дня, а не от прошлого срока: якорь 31 даёт 31 января, 28 (29) февраля, 31 марта, 30 апреля.
- Другие периоды добавляются той же формулой: квартал и год - это шаг 3 и 12 месяцев, неделя - `schedule_first_due_date + 7 * (seq - schedule_from_seq)`.

### Досоздание периодов

- Инвариант: у активного платежа есть все периоды со сроком до сегодня включительно и ровно один период со сроком позже сегодня.
- Поэтому "следующий период с отдельным статусом" виден сразу, а просрочка не останавливает следующие периоды.
- Досоздание идёт при создании платежа и на каждом тике планировщика. Если сервер простоял месяц, тик досоздаст все пропущенные периоды. Повтор безопасен благодаря `unique (recurring_payment_id, seq)`.

### Просрочка

- Не оплачен и `сегодня > due_date`: просрочен.
- Оплачен и `paid_on > due_date`: оплачен с просрочкой.
- Оплата в день срока - вовремя.
- Исправление `paid_on` сразу меняет результат, `due_date` не трогается.
- "Сегодня" считается в часовом поясе `TZ` из `.env`.

### Окно напоминания

- Период подходит для напоминания, если: не оплачен, платёж не прекращён, `сегодня <= due_date <= сегодня + окно`. Окно - своё у платежа (`reminderDaysBefore`), иначе общее: заданное в панели, иначе `REMINDER_DAYS_BEFORE` (по умолчанию 3).
- Платёж, добавленный позже чем за 3 дня до срока, сразу попадает в окно и получает напоминание в той же транзакции создания.
- К оплаченному периоду можно приложить чек (PDF или снимок до 10 МБ) в панели, через API или ответом боту; файл лежит в S3-совместимом хранилище, отмена оплаты удаляет чек (ADR-017).
- **Напоминание о просрочке:** одно, в первый день просрочки неоплаченного периода действующего платежа (`kind = overdue`), тем же получателям. Именно эту проблему кейс и решает: бухгалтерия забыла оплатить.
- Дата ближайшей оплаты при создании платежа не может быть раньше сегодня (400), как и при изменении. Просроченные периоды для демо создаёт команда тестовых данных.

### Изменение платежа

`PATCH /recurring-payments/{id}`, только администратор. В кейсе этой операции нет, добавляем сами. Правило: правка меняет будущее и никогда не переписывает историю.

- **Затрагиваются** только неоплаченные периоды со сроком сегодня или позже: они ещё не стали просроченными. Оплаченные и просроченные периоды не меняются.
- **Название** меняется у самого платежа, поэтому новое название видно и в истории.
- **Сумма и валюта** переписываются в затронутых периодах.
- **Расписание** (дата ближайшей оплаты, а с ней якорный день): затронутые периоды удаляются вместе с их ожидающими напоминаниями. Новый отрезок начинается с `schedule_from_seq` = последний оставшийся номер + 1 (или 0, если периодов не осталось) и `schedule_first_due_date` = новая дата. Затем досоздание по инварианту. Новая дата не может быть раньше сегодня.
- Если новый срок попал в окно напоминания, напоминание уходит по новому периоду. Это не дубль: изменился сам срок.
- Прекращённый платёж не меняется: 409.
- Всё в одной транзакции, старые и новые значения - в журнал.

### Прекращение платежа

- `DELETE /recurring-payments/{id}` ставит `stopped_at`, удаляет будущие неоплаченные периоды (срок позже сегодня) и отменяет их ожидающие напоминания. Прошлые и оплаченные периоды остаются.
- Всё в одной транзакции: после ответа API напоминание о прекращённом платеже уйти не может (отправитель ещё раз проверяет условия перед отправкой, раздел 6).

## 5. Авторизация через Aéza

Уточнение к кейсу: своя база пользователей не нужна, если вход идёт через Aéza и на нём показан весь сценарий (уточнения в [Case.md](Case.md), ADR-014). Пароли, 2FA и сброс пароля остаются у Aéza. У нас - белый список "кто может войти и с какой ролью" и свои короткие сессии.

### API Aéza

Проверено на тестовом аккаунте хакатона (2026-10-24), адрес `AEZA_API_URL=https://my.aeza.ru/api`:

| Вызов | Что возвращает |
| --- | --- |
| `POST /v2/auth/login` с `{email, password}` | `{challenge, requirements}`; пустой `requirements` - 2FA не нужна; неверный пароль - 400 `invalid_credentials` |
| `POST /v2/auth/use-challenge` с `{challenge}` | `{session, expiresAt}`, сессия примерно на 30 дней |
| `GET /v2/auth/tfa?challenge=`, `POST /v2/auth/tfa/totp` | способы 2FA и вход с кодом (по коду кабинета Aéza, на аккаунте с 2FA не проверено) |
| `GET /v2/accounts/me` | `id`, `email`, `roles` и данные аккаунта; принимает `Authorization: Bearer <session>` и `X-API-KEY` |
| `POST /v2/auth/logout` | 204, сессия Aéza закрыта |

- У v1 рабочий путь `/api/...`, а не `/api/v1`, как в их спецификации.
- Сессия и ключ Aéza дают полный доступ к аккаунту хостинга. Поэтому сессию Aéza backend закрывает сразу после входа, а `X-API-KEY` не хранит.

Точный контракт для frontend (запросы, ответы, коды ошибок, хранение токена) - в [openspec/changes/archive/2026-10-24-backend-aeza-auth/design.md](../openspec/changes/archive/2026-10-24-backend-aeza-auth/design.md); после реализации - в `backend/api/openapi.yaml`.

### Схема входа

| Шаг | Кто | Что происходит |
| --- | --- | --- |
| Шаг 1 | frontend | `POST /api/v1/auth/login` с email и паролем аккаунта Aéza |
| Проверка пароля | backend | `v2/auth/login` в Aéza; её ответ `{challenge, requirements}` уходит клиенту как есть (ADR-015) |
| Шаг 2 | frontend | пустой `requirements` - `POST /api/v1/auth/use-challenge` с `challenge`; иначе `POST /api/v1/auth/tfa/totp` с `challenge` и кодом 2FA |
| Сессия Aéza | backend | `v2/auth/use-challenge` или `v2/auth/tfa/totp`, затем `v2/accounts/me` и сразу `v2/auth/logout` |
| Белый список | backend | участник по `aeza_account_id`, иначе по email (тогда id привязывается); нет или отключён - 403 `not_a_member` |
| Своя сессия | backend | случайный токен, в `sessions` только хеш; ответ `{session, expiresAt}`, как у Aéza |
| Запрос к API | frontend | `Authorization: Bearer <session>`; проверка - запрос в свою базу, без Aéza |
| Выход | frontend | `POST /api/v1/auth/logout`: сессия удаляется |
| Профиль | backend | `GET /api/v1/auth/me`: id участника, email и роль |

- Срок сессии - `SESSION_TTL_HOURS`, по умолчанию 12 часов, без продления: на следующий день бухгалтер входит заново.
- Токен - непрозрачная строка, не JWT: frontend ничего из него не читает, роль и email берёт из `GET /auth/me`.
- Пароль и `challenge` не сохраняются и не попадают в журнал.
- **Ограничение неудачных входов.** Все входы уходят в Aéza с одного адреса - нашего сервера, а у WAF Aéza есть бан IP за неудачные входы. Применяется ли он к их входу и какой у него порог, неизвестно (раздел 12, вопрос 16). Поэтому backend считает неудачные входы сам и при превышении отвечает 429, не обращаясь к Aéza: не больше 5 за 10 минут на email и на IP клиента, и не больше 20 за 10 минут на весь сервер. Общий предел на время закрывает вход всем, но это короче и предсказуемее, чем бан IP у Aéza. Счётчики - в PostgreSQL, чтобы их видели все экземпляры `api`.
- Капчи на входе Aéza сейчас не требует. Если включит, понадобится виджет Turnstile в панели и передача `X-Captcha-Token` (раздел 11).

### Другие системы: X-API-KEY

- Система (например, 1С) передаёт `X-API-KEY` - ключ своего аккаунта Aéza из кабинета ("API ключи").
- Backend проверяет ключ через `v2/accounts/me` и запоминает ответ на 60 секунд по хешу ключа. Аккаунт должен быть в белом списке, обычно с ролью `integration`.
- Ключ даёт полный доступ к аккаунту Aéza, поэтому для интеграции заводится отдельный аккаунт. Наш backend ключ не хранит и не пишет в журнал.
- В Swagger две схемы: `bearer` (токен из `POST /auth/login`) и `X-API-KEY`.

### Роли и права

Роли хранятся в белом списке: `admin`, `user`, `integration`.

| Операция | Пользователь | Администратор | integration |
| --- | --- | --- | --- |
| Вход, `me`, выход | да | да | `me` |
| Список платежей и периодов, итоги, отделы | да | да | да |
| Отметка и отмена оплаты, исправление фактической даты | да | да | да |
| Создание, изменение и прекращение регулярного платежа | нет (403) | да | да |
| Белый список (`/users`) и запись отделов | нет (403) | да | нет (403) |
| Личный Telegram (`/me/telegram`) | да | да | нет (403) |
| Изменение или удаление администратора из `.env` | нет | нет (409) | нет |

- Право проверяется на сервере для каждой операции. Скрытая кнопка во frontend защитой не считается.
- Без действующей сессии или ключа - 401 `not_auth` на всём `/api/v1`, кроме Swagger и шагов входа (`login`, `use-challenge`, `tfa/totp`).

### Белый список через API

`/api/v1/users` - управление участниками (таблица `members`), паролей там нет.

- `GET /users`: участники с ролями `user` и `integration`.
- `POST /users`: email аккаунта Aéza и роль `user` или `integration`. Роль `admin` через API не назначается. Существование аккаунта в Aéza не проверяется: проверка случится при его первом входе.
- `PATCH /users/{id}`: роль, включён или отключён. Отключение сразу удаляет сессии участника.
- `DELETE /users/{id}`: удаление участника, его сессий и привязки Telegram. История оплат остаётся с сохранённым email.
- Операции над администратором из `.env` отклоняются с 409.

### Администраторы из `.env`

`ADMIN_EMAILS` - email аккаунтов Aéza через запятую. При каждом старте `api` синхронизирует их в `members`:

1. Для каждого email строка с ролью `admin` и `source = env` создаётся или обновляется.
2. Строки `source = env`, чьих email в списке больше нет, удаляются вместе с сессиями.

Повторный старт ничего не ломает. Синхронизация идёт в своей базе, до приёма запросов; Aéza для неё не нужна.

### Сбои

- Неверный или истёкший токен: 401 `not_auth`, frontend отправляет на вход.
- Неверный пароль: 400 `invalid_credentials`, так же для несуществующего аккаунта (как у Aéza). Истёкший `challenge` - 400 `invalid_challenge`, неверный код 2FA - 400 `invalid_code`.
- Верный пароль, но аккаунта нет в белом списке или он отключён: 403 `not_a_member`.
- API Aéza недоступен: войти нельзя (503 `identity_unavailable`), уже выданные сессии работают; `X-API-KEY` работает до конца 60 секунд кеша, потом 503.

## 6. Напоминания: outbox и отправка

### Получатели

Из Telegram можно отметить оплату и отложить напоминание на завтра: человека, нажавшего кнопку, система узнаёт по его личной привязке (ADR-010). Остальные действия - только в панели.

- **Общий чат** - чат бухгалтерии из `TELEGRAM_CHAT_ID` в `.env`. Это сценарий кейса, бот добавлен в чат заранее. Если переменная пуста, общий чат выключен.
- **Личный чат** - каждый пользователь (и администратор) сам решает, получать ли напоминания лично. Для этого он привязывает Telegram и держит включённым `personal_enabled`.
- Каналы независимы: один и тот же период может прийти и в общий чат, и в личные. В личный чат приходят напоминания обо всех платежах: список общий.

### Привязка личного чата

Бот не может написать человеку первым, поэтому привязку начинает сам пользователь:

1. В веб-панели "Подключить Telegram": backend создаёт одноразовый код (10 минут) и отдаёт ссылку `https://t.me/<бот>?start=<код>`. Имя бота backend узнаёт при старте через `getMe`.
2. Пользователь открывает ссылку и нажимает "Запустить". Боту приходит `/start <код>`.
3. Backend находит код, проверяет срок, помечает использованным и записывает `chat_id` в `telegram_links`. Бот отвечает: "Готово, напоминания будут приходить сюда". Панель показывает привязку после перечитывания.
4. `/start` без кода, с просроченным или чужим кодом - бот отвечает подсказкой "откройте ссылку из веб-панели" и ничего не привязывает.

- Входящие сообщения бот получает long polling (`getUpdates`, aiogram) в процессе `worker`: публичный webhook не нужен. Telegram разрешает только один `getUpdates` на токен, поэтому опрос ведёт один экземпляр `worker` под advisory-блокировкой PostgreSQL.
- Запросы к Telegram идут через прокси из `TELEGRAM_PROXY_URL`, если он задан: и отправка, и чтение обновлений.
- Отвязка: в панели или командой `/stop` в боте.
- Если пользователя удалили в системе, его привязка удаляется в той же операции.
- Сообщения в общем чате бот не читает и в нём на команды не отвечает.

### Постановка

Раз в минуту (и в транзакции создания или изменения платежа) один запрос вставляет в `notifications` строки для всех периодов в окне: одну для общего чата, если он настроен, и по одной на каждого пользователя с привязкой, `personal_enabled` и без `blocked_at`. `insert ... select ... on conflict do nothing`: дубль невозможен из-за `unique`.

Пользователь, привязавший Telegram, когда окно уже началось, получит напоминание на следующем тике, если срок ещё не прошёл.

### Отправка

1. Взять пачку `pending` с `next_attempt_at <= now()` через `for update skip locked`. Два экземпляра backend не возьмут одну строку.
2. Заново проверить условия в той же транзакции: период мог оплатиться, платёж прекратиться, а пользователь отключить личные напоминания или отвязать Telegram. Если условия больше не выполняются, строка становится `cancelled`.
3. Определить чат получателя и отправить: название, сумма, валюта, срок.
4. Успех: `sent`, `sent_at`, `external_id`. Временная ошибка (сеть, 5xx, 429): `attempts + 1`, `next_attempt_at` с растущей паузой, для 429 - время из ответа Telegram. Окончательная ошибка (чат не найден, бот удалён из чата): `failed` с причиной в `last_error`. Ответ "бот заблокирован пользователем" ставит `blocked_at` в привязке.
5. Между сообщениями в один чат - пауза по ограничениям Telegram (около 1 в секунду в личный чат, 20 в минуту в группу). Паузы ведутся по чатам: занятый чат не задерживает остальные.

**Гарантия.** Доставка "хотя бы один раз". Повтор возможен только при падении процесса между ответом Telegram и коммитом: для напоминаний потерять сообщение хуже, чем отправить его дважды. Обычные повторы, перезапуски и второй экземпляр дублей не создают.

**Повторная отметка.** Если оплату отменили, а напоминание по периоду уже было, второе не отправляется: напоминание одно на период для каждого получателя. Это допущение (раздел 12).

**Секреты.** Токен бота не попадает в журнал и в `last_error`: перед записью он заменяется на `***`.

## 7. Контракт API

- Контракт выгружается из кода (ADR-002, ADR-013): схемы Pydantic и роутеры FastAPI - источник истины, `backend/api/openapi.yaml` - их копия, которую выгружает команда и сверяет тест. Swagger на `/api/v1/docs`.

Соответствие эндпоинтам кейса (таблицу стоит показать жюри):

| Эндпоинт кейса | В решении |
| --- | --- |
| `POST /auth/login` | как в кейсе: email и пароль аккаунта Aéza, ответ Aéza `{challenge, requirements}` |
| - | добавлены `POST /auth/use-challenge` и `POST /auth/tfa/totp`: второй шаг входа, как у Aéza, ответ `{session, expiresAt}` |
| `GET /auth/me` | как в кейсе: id участника, `email` и роль (поле `login` заменено на `email`) |
| `POST /auth/logout` | как в кейсе: сессия удаляется |
| `GET`, `POST /recurring-payments` | как в кейсе |
| `DELETE /recurring-payments/{id}` | как в кейсе: прекращение с сохранением истории |
| - | добавлен `PATCH /recurring-payments/{id}`: изменение платежа (раздел 4) |
| - | добавлен `GET /recurring-payments/{id}`: данные платежа для формы изменения |
| `GET /payment-occurrences`, `GET`, `PATCH /payment-occurrences/{id}` | как в кейсе |
| `GET /payments/summary` | как в кейсе |
| `GET`, `POST /users`, `PATCH`, `DELETE /users/{id}` | как в кейсе, но без паролей: белый список аккаунтов Aéza с ролями |
| `GET /docs` | как в кейсе, Swagger со схемами `bearer` и `X-API-KEY` |
| - | добавлены `/me/telegram`: личные напоминания (ниже) |
| - | добавлены `/departments`: отделы (ниже) |

- Первым шагом backend пишет роутеры и схемы всех эндпоинтов с заглушками и выгружает `openapi.yaml`. Пока логики нет, frontend работает с mock-сервером из этого файла (например, Prism). Так обе части пишутся параллельно с первого дня.
- **Формат как у Aéza v2 (ADR-015).** JSON в camelCase (тела и параметры запроса: `amountMinor`, `nextDueDate`, `recurringPaymentId`). Список - `{items, total}` с параметрами `limit` и `offset`. Ошибка - `{statusCode, message, error, timestamp, path, payload, requestId}`: `error` - код для программы, `message` - текст на русском, `payload` - список `{field, message}` для 400 `bad_request`, `{entity, id}` для 404 `not_found`, иначе текст. Ошибки проверки данных - 400, а не 422. В разделах этого плана имена полей могут быть даны в snake_case, как в коде; в JSON они в camelCase.
- Точные примеры запросов и ответов для frontend - в [openspec/changes/archive/2026-10-24-backend-aeza-auth/design.md](../openspec/changes/archive/2026-10-24-backend-aeza-auth/design.md), после реализации - в `backend/api/openapi.yaml`.
- `GET /payment-occurrences`: фильтры `status` (`paid`, `unpaid`, `overdue`), `currency`, `recurringPaymentId`, `departmentId`, `from`, `to`; сортировка по сроку; пагинация.
- `PATCH /payment-occurrences/{id}`: `{ "paid": true, "paidOn": "2026-10-23" }` - отметить или исправить дату; `{ "paid": false }` - отменить. Без `paidOn` берётся сегодня. Дата оплаты позже сегодня отклоняется (допущение).
- `GET /payments/summary`: по каждой валюте отдельно - к оплате, оплачено, просрочено; необязательные `from`, `to` и `departmentId`. Это же закрывает дополнительную возможность "итоги на дату".
- В ответе периода есть вычисленные поля `overdue` и `days_overdue`, чтобы frontend не повторял правила домена.
- Личные напоминания, каждый пользователь управляет только своими:
  - `GET /me/telegram` - привязан ли Telegram, имя в Telegram, включены ли личные напоминания, заблокирован ли бот;
  - `POST /me/telegram/link` - новый одноразовый код и ссылка на бота; прежний неиспользованный код перестаёт действовать;
  - `PATCH /me/telegram` - `{ "personal_enabled": false }` включить или выключить личные напоминания;
  - `DELETE /me/telegram` - отвязать Telegram.
- Отделы (ADR-012): `GET /departments` - всем; `POST /departments`, `PATCH`, `DELETE /departments/{id}` - только администратору. `department_id` - необязательное поле в создании и изменении платежа.

### Встраивание

Система ставится on-premise и должна встраиваться в инфраструктуру заказчика (ADR-011).

**Входящее.**

- Другие системы (например, 1С) ходят в API с `X-API-KEY` своего аккаунта Aéza, добавленного в белый список с ролью `integration`. Ей доступны чтение, создание, изменение и прекращение платежей, отметка оплаты. Пользователями и отделами она не управляет.
- `POST` принимает заголовок `Idempotency-Key`: повтор с тем же ключом и телом возвращает прежний ответ, с другим телом - 422.
- Сотрудники входят аккаунтами Aéza (ADR-014). Вход через Active Directory или LDAP не предусмотрен.

**Исходящее: интеграционные события.**

| Событие | Когда |
| --- | --- |
| `payment.created`, `payment.updated`, `payment.stopped` | создание, изменение, прекращение платежа |
| `occurrence.due_soon` | период вошёл в окно напоминания |
| `occurrence.paid`, `occurrence.unpaid` | отметка оплаты (в том числе исправление даты) и её отмена |
| `occurrence.overdue` | первый день просрочки неоплаченного периода |

- Формат: `id`, `type`, `schema_version`, `occurred_at`, `data` (платёж, период, отдел, сумма в минимальных единицах, валюта, срок, дата оплаты). Без персональных данных, кроме логина автора действия.
- Событие пишется в `integration_events` в той же транзакции, что и изменение. События по времени (`due_soon`, `overdue`) ставит планировщик, `dedup_key` не даёт выпустить их дважды.
- Адаптеры за интерфейсом `EventPublisher`, каждый включается своей настройкой в `.env`:
  - **webhook** - HTTP POST JSON на `WEBHOOK_URL`, заголовок `X-Signature` с HMAC-SHA256 тела по `WEBHOOK_SECRET`, повторы с растущей паузой при ошибке сети и ответах 5xx и 429;
  - **Kafka** - публикация в топик `KAFKA_TOPIC` брокера `KAFKA_BROKERS` заказчика; ключ сообщения - идентификатор платежа, поэтому события одного платежа читаются по порядку.
- Доставка "хотя бы один раз": получатель отбрасывает повтор по `id` события.
- RabbitMQ и другие брокеры не делаем. Если у заказчика другой брокер, это ещё одна реализация `EventPublisher`, ядро не меняется.
- В нашем compose Kafka запускается только в профиле `integration` и изображает брокер заказчика для демо. По умолчанию профиль выключен и не утяжеляет запуск у жюри.

## 8. Frontend

- **Вход.** Своя форма в два шага, как у Aéza: email и пароль аккаунта Aéza (`login`), затем сразу `use-challenge` или, если `requirements` не пуст, поле кода 2FA (`tfa/totp`). Подсказка, что это аккаунт my.aeza.ru. Ответ 403 объясняет, что доступ выдаёт администратор. Токен сессии - в `sessionStorage`: переживает обновление страницы, пропадает с закрытием вкладки. Ответ 429 показывает, через сколько минут повторить (`Retry-After`). Кнопка "Выйти" вызывает `POST /auth/logout`.
- **Платежи** (главная). Список периодов: название, сумма, валюта, срок, статус, дата оплаты, просрочка, отдел. Фильтры (в том числе по отделу), отметка оплаты в одно действие, исправление даты, отмена отметки. Сверху итоги по валютам с учётом выбранного отдела.
- **Регулярные платежи** (только администратор). Создание, изменение, прекращение с подтверждением, история периодов платежа, выбор отдела. В форме изменения пояснение: правка касается только будущих неоплаченных периодов.
- **Пользователи** (только администратор). Белый список: добавить email аккаунта Aéza с ролью, сменить роль, отключить, удалить. Паролей нет.
- **Отделы** (только администратор). Создание, переименование, удаление с предупреждением, что платежи останутся без отдела.
- **Уведомления** (каждый пользователь). "Подключить Telegram" открывает ссылку на бота, после привязки видно имя в Telegram, переключатель "Присылать мне лично" и "Отвязать". Если бот заблокирован, страница объясняет, как его снова запустить. Там же видно, подключён ли общий чат.
- Роль берётся из `/auth/me` и только скрывает недоступные действия. Права решает сервер.
- Ответ 401 на любом запросе ведёт на страницу входа.
- Суммы переводятся из минимальных единиц в одном месте, даты срока не проходят через часовой пояс браузера.
- После своей записи список перечитывается, при возврате на вкладку тоже.

## 9. Надёжность и эксплуатация

### Метрики и логи

- Backend публикует `/metrics` только во внутренней сети Compose. Prometheus опрашивает его каждые 15 секунд и хранит временные ряды в отдельном именованном томе.
- Минимальный набор метрик: число и длительность HTTP-запросов по шаблону маршрута, методу и коду ответа; время последнего успешного тика планировщика; число созданных периодов; размер и возраст старейшей записи outbox; успешные, повторные и окончательно неудачные отправки уведомлений; ошибки PostgreSQL, API Aéza и Telegram; неудачные входы по причине.
- Метрики не содержат `user_id`, `payment_id`, логин, полный URL, текст ошибки и другие значения с высокой кардинальностью.
- Все сервисы пишут JSON-логи в `stdout`/`stderr`. Общие поля: `timestamp`, `level`, `service`, `message`, `request_id`; фоновые операции используют отдельный `operation_id`.
- Promtail читает Docker-логи, добавляет метки `service`, `environment`, `level` и отправляет их в Loki. Содержимое сообщения не превращается в метки.
- Loki работает в однопроцессном режиме с файловым хранилищем и ограниченным сроком хранения. Его данные лежат в отдельном именованном томе.
- Grafana автоматически получает provisioned data sources Prometheus и Loki и стартовый dashboard `Invoice Keeper` из файлов репозитория. Ручная настройка после `docker compose up` не требуется.
- Dashboard показывает доступность backend, RPS, p95 длительности запросов, долю 5xx, состояние планировщика, размер и возраст outbox, результаты отправки в Telegram. Для диагностики используются Grafana Explore и поиск логов по `service`, `level`, `request_id` и временному интервалу.
- Prometheus и Loki не публикуются через Caddy. Grafana открыта на `grafana.<домен>` через Caddy и закрыта паролем администратора из `.env`, регистрация и анонимный вход выключены (ADR-009).
- Недоступность Prometheus, Loki, Promtail или Grafana не блокирует запуск и работу API, планировщика и Telegram-уведомлений.
- Версия Promtail закреплена: агент достиг EOL 2 марта 2026 года. После хакатона его конфигурация переносится в Grafana Alloy; приложение при этом не меняется.

### Эксплуатационные гарантии

- **Порядок старта в compose:** PostgreSQL, затем `migrate` (одноразовый запуск Alembic), затем `api` и `worker`. Compose ждёт `readyz` у `api`.
- **Два процесса backend из одного образа:** `api` (uvicorn) и `worker`. Без `worker` API работает, но периоды не досоздаются, напоминания и события не отправляются; это видно по метрике времени последнего тика.
- **Профили compose:** без профиля - всё, что нужно по кейсу; `integration` - Kafka для демо интеграции. Webhook, Kafka и наблюдаемость не входят в `readyz`: их сбой не останавливает приложение.
- **Миграции** применяет отдельный одноразовый сервис `migrate` (`alembic upgrade head`) до старта `api` и `worker`. Повторный запуск ничего не ломает, а два процесса не гонят миграции наперегонки.
- **Health:** `/healthz` - процесс жив; `/readyz` у `api` - база доступна, миграции применены. API Aéza в `readyz` не входит: без него не работает только вход. У `worker` свой `/healthz` и время последнего успешного тика в метриках.
- **Корректная остановка:** по сигналу `api` перестаёт брать новые запросы, `worker` - новые строки outbox; оба дожидаются текущих.
- **Журнал** в JSON. Без паролей, токенов сессий, ключей Aéza, токена бота и персональных данных, не нужных для диагностики.
- **Сохранность:** данные PostgreSQL в именованном томе. Перезапуск compose ничего не теряет (критерий приёмки).
- **Память и диск:** Prometheus, Loki и Grafana получают лимиты ресурсов в compose. Для Prometheus и Loki задаются сроки хранения; перед выкладкой проверяется свободное место.
- **Конфигурация** только из `.env`. `.env.example` без секретов, со всеми переменными и комментариями: база, `ADMIN_EMAILS`, `AEZA_API_URL`, `SESSION_TTL_HOURS`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` (общий чат, необязательно), `TELEGRAM_PROXY_URL` (необязательно), `TZ`, `REMINDER_DAYS_BEFORE`, учётная запись Grafana и сроки хранения Prometheus/Loki, необязательные `WEBHOOK_URL`, `WEBHOOK_SECRET`, `KAFKA_BROKERS`, `KAFKA_TOPIC`. Backend не стартует при отсутствии обязательной переменной и называет её в ошибке.

## 10. Тестирование

Каждый критерий приёмки закрыт автоматическим тестом.

| Критерий | Тест |
| --- | --- |
| Последний день месяца, якорь 31, високосный год | табличный unit-тест расчёта срока |
| Просрочка со следующего дня, оплата в день срока вовремя | unit-тест просрочки |
| Исправление даты убирает просрочку | API-тест `PATCH` |
| Следующий период с отдельным статусом, прошлые сохраняются | тест досоздания с `Clock`, сдвинутым на месяц |
| Пользователь не выполнит действия администратора через API | API-тест: каждая админская операция под пользователем даёт 403 |
| Без авторизации данные недоступны | API-тест: каждый эндпоинт без токена, с неизвестным и с истёкшим токеном, с неверным `X-API-KEY` даёт 401 |
| Удалённый или отключённый участник теряет доступ | API-тест: после отключения и удаления его токен сразу даёт 401 |
| Вход только из белого списка | тест с фейковым API Aéza: верный пароль без записи в списке - 403, с записью - токен; 2FA - второй шаг; сессия Aéza закрыта |
| Перебор паролей ограничен | тест: шестой неудачный вход за 10 минут на email - 429, двадцать первый на сервер с разных email и IP - 429, до Aéza эти запросы не доходят |
| Изменение платежа не трогает оплаченные и просроченные периоды | API-тест `PATCH /recurring-payments/{id}` с суммой и с новой датой |
| Администратор из `.env` не меняется через API | API-тест: 409 на изменение и удаление; email, убранный из `ADMIN_EMAILS`, теряет доступ |
| Напоминание за 3 дня, без дублей | тест: два тика планировщика и два отправителя параллельно, фейковый `Notifier` получил одно сообщение на каждого получателя |
| Общий и личные чаты независимы | тест: общий чат и два пользователя, один с выключенными личными напоминаниями; сообщения получили общий чат и только второй пользователь |
| Привязка Telegram | тест: `/start` с верным кодом привязывает, с просроченным, использованным и чужим кодом - нет; отключение личных напоминаний отменяет ожидающие |
| Напоминание о просрочке | тест с `Clock`: в первый день просрочки одно напоминание `overdue`, на следующий день и после отмены оплаты - новых нет |
| Дата в прошлом отклоняется | API-тест: создание и изменение платежа с датой раньше сегодня и отметка оплаты датой позже сегодня дают 422 |
| `openapi.yaml` совпадает с кодом | тест сравнивает файл с `app.openapi()` |
| Пользователь заблокировал бота | тест: ответ Telegram "заблокирован" ставит `blocked_at`, следующих напоминаний этому пользователю нет, общий чат получает свои |
| Поздний платёж получает напоминание сразу | API-тест создания со сроком через 1 день |
| Оплаченный и прекращённый платёж не напоминают | тест отправителя с повторной проверкой |
| Итоги отдельно по валютам | API-тест `summary` |
| Сохранение после перезапуска | тест на настоящем PostgreSQL в контейнере; вручную - `docker compose restart` |
| Метрики backend доступны Prometheus | интеграционный тест `/metrics` и проверка обязательных серий через Prometheus API |
| Логи доступны в Grafana через Loki | smoke-тест: записать событие с тестовым `request_id`, дождаться доставки и найти его через Loki API |
| Секреты не попадают в логи | тест логирования запросов с Bearer-токеном и токеном бота; значения отсутствуют в выводе |
| Событие пишется вместе с изменением | тест: откат транзакции изменения не оставляет события; `occurrence.overdue` на двух тиках записан один раз |
| Webhook подписан и повторяется | тест с локальным HTTP-сервером: подпись `X-Signature` верна, после ответа 500 событие приходит повторно с тем же `id` |
| Kafka получает события по порядку | интеграционный тест с Kafka в контейнере: события одного платежа в одной партиции по порядку |
| Повтор `POST` с `Idempotency-Key` | API-тест: второй запрос с тем же ключом возвращает тот же платёж, с другим телом - 422 |
| Роль `integration` ограничена | API-тест: платежи доступны, пользователи и отделы - 403 |
| Удаление отдела не трогает платежи | API-тест: платежи остались без отдела, фильтр по отделу и итоги считают верно |

- Unit-тесты домена не требуют базы и работают за секунды.
- Интеграционные тесты идут на настоящем PostgreSQL в контейнере, без моков базы: `for update skip locked` и `on conflict` на моке не проверить.
- API Aéza в тестах заменяет фейковый `IdentityProvider`. Клиент Aéza проверяется на локальном HTTP-приёмнике с ответами, снятыми с настоящего API; ручная проверка на тестовом аккаунте - перед сдачей.
- Перед сдачей - smoke-скрипт сценария защиты через API (раздел 14).

## 11. Риски

| Риск | Что делаем |
| --- | --- |
| API Aéza недоступен на демо | выданные сессии работают без него; войти заранее, до защиты; `readyz` от Aéza не зависит |
| Aéza меняет или включает капчу на входе | вход через `X-API-KEY` в Swagger как запасной путь; виджет капчи в панели, если успеем |
| WAF Aéza банит IP сервера за неудачные входы: все входы идут с одного адреса, войти не сможет никто | свои пределы неудачных входов: на email, на IP клиента и общий на сервер (раздел 5); попросить Aéza внести IP сервера в исключения WAF; на защиту войти заранее, выданные сессии бана не боятся |
| Утечка ключа или сессии Aéza с правами на хостинг | сессия Aéza закрывается сразу после входа, ключ не хранится и не пишется в журнал, для интеграции - отдельный аккаунт |
| Кража токена из браузера через XSS | токен в `sessionStorage`, а не в `localStorage` и cookie; CSP в Caddy; срок сессии 12 часов; выход и отключение участника удаляют сессию на сервере |
| Посторонний клиент Aéza входит в систему | белый список: без записи в `members` - 403 |
| Telegram недоступен на демо | outbox повторит отправку; на демо заранее проверить бота и чат |
| Telegram заблокирован у заказчика или на сервере | `TELEGRAM_PROXY_URL` (SOCKS5 или HTTP) для отправки и чтения обновлений; проверить прокси на стенде заранее |
| `openapi.yaml` разошёлся с кодом | тест сравнивает файл с тем, что строит приложение; файл выгружается командой |
| Promtail больше не поддерживается | закрепить проверенную версию и хранить конфигурацию отдельно; после хакатона перенести её в Grafana Alloy |
| Метрики разрастаются из-за высокой кардинальности | разрешить только ограниченные метки; не использовать ID, логины, полный URL и тексты ошибок |
| Prometheus или Loki заполняют диск | отдельные тома, ограниченный retention, лимиты ресурсов и контроль свободного места |
| Сбой контура наблюдаемости влияет на приложение | Prometheus только опрашивает backend, логирование не ждёт Loki; observability-сервисы не входят в `readyz` приложения |
| Два экземпляра backend читают обновления бота, Telegram отвечает 409 | `getUpdates` ведёт один экземпляр под advisory-блокировкой |
| Чужой человек привязывает Telegram к чужому пользователю | код одноразовый, живёт 10 минут, выдаётся только вошедшему пользователю, в базе только хеш |
| Kafka утяжеляет запуск у жюри | Kafka только в профиле `integration`, по умолчанию выключена |
| Внешняя система получает событие дважды | в событии `id` для отбрасывания повтора; это описано в README для интеграторов |
| Изменение формата события ломает интеграцию | `schema_version` в событии; поля только добавляются, удаление - новая версия |

## 12. Вопросы по кейсу

"Допущение" - наш вариант по умолчанию, чтобы не стоять на месте. "Уточнение" - ответ на вопрос (цитаты в [Case.md](Case.md), раздел уточнений). "Решение команды" - вопрос закрыт командой без уточнения.

1. Можно ли создать платёж с датой ближайшей оплаты в прошлом? Решение команды: нет, 400. Поле называется "дата ближайшей оплаты", а опечатка в прошлом создала бы пачку ложных просрочек. Просрочки для демо создаёт команда тестовых данных.
2. Нужно ли напоминать о просроченном неоплаченном периоде? Решение команды: да, одно напоминание в первый день просрочки (раздел 4). Это и есть проблема кейса: бухгалтерия забыла оплатить.
3. Отменили оплату после напоминания: напоминать снова? Решение команды: нет, одно напоминание каждого вида на период каждому получателю.
4. Может ли фактическая дата оплаты быть позже сегодня? Решение команды: нет, 400.
5. Что видно о периодах прекращённого платежа? Допущение: прошлые периоды остаются в списке с пометкой "платёж прекращён", просрочка по ним продолжает считаться.
6. Делать ли действия в Telegram, например кнопку "Оплачено"? Уточнение: дублирование функционала в Telegram опционально, но "пользователь тг не связан с учеткой". Решение команды: сначала только уведомления; 2026-10-25 добавлены кнопки "Оплачено" и "Напомнить завтра" для участников с личной привязкой (ADR-010).
7. Продукт для одной группы с общим списком платежей или с личными пространствами у каждого? Уточнение: сценарий ровно как в кейсе, "условная бухгалтерия забывает оплатить регулярные счета". Одна установка - одна компания, общий список. Личные напоминания в Telegram - наше расширение поверх общего чата (раздел 6).
8. Должен ли администратор подтверждать отметки оплаты пользователей? Уточнение: не должен, это излишество. Отметка пользователя действует сразу.
9. Можно ли пользователю в веб-панели самому привязать свой Telegram только для получения напоминаний в личку, без прав и действий через Telegram? Решение команды: да, ветка А (ADR-010). Telegram только доставляет, прав и действий через бота нет.
10. Multi-tenancy или on-premise у одного клиента? Уточнение: on-premise. Одна установка - одна компания (ADR-001).
11. Большая ли нагрузка, нужны ли микросервисы и брокер? Уточнение: архитектуру решаем сами, нагрузка у уведомлений небольшая; думать в сторону встраивания, "наличие того же MQ может повернуть решение". Решение команды: монолит без внутреннего брокера, Kafka и webhook как каналы интеграции (ADR-011).
12. Нужно ли деление по отделам? Уточнение: как дополнительная фича можно, но система не должна на этом сильно завязываться. Решение команды: делаем отделы как слабо связанную фичу (ADR-012).
13. Можно ли заменить `POST /auth/login` и `POST /auth/logout` входом и выходом через Keycloak (OIDC)? Уточнение: можно (раздел 7). Позже заменено пунктом 14.
14. Нужна своя база пользователей или вход по аккаунтам Aéza? Уточнение (2026-10-24): своя база не нужна, если есть авторизация через Aéza и на ней показан весь сценарий. Токены Aéza выдаются "через челендж". Решение команды: вход через Aéza и белый список участников (ADR-014, раздел 5).
15. Для демо входа администратором и пользователем нужны два аккаунта Aéza, а тестовый аккаунт хакатона один. Допущение: второй аккаунт получить у организаторов или зарегистрировать; до этого сценарий показывается под одним аккаунтом со сменой роли в белом списке.
16. Банит ли WAF Aéza IP за неудачные входы в `auth/login` и с какого порога, можно ли внести IP нашего сервера в исключения? Допущение: банит; держим свои пределы ниже (раздел 5).

## 14. Сценарий защиты

Сверять перед сдачей, каждый шаг вживую. Его же повторяет smoke-скрипт через API.

1. Вход администратором: email и пароль аккаунта Aéza из `ADMIN_EMAILS`.

## 15. Тестовые данные

Требование кейса: аренда в RUB, сервер в USD, подписка в EUR. Даты считаются от дня запуска, а не зашиты в файл, иначе через неделю демо сломается.

- аренда, RUB: прошлый период оплачен вовремя, текущий просрочен на 5 дней;
- сервер, USD: срок через 2 дня, в окне напоминания;
- подписка, EUR: якорный день 31, прошлый период оплачен с опозданием;
- участник с ролью `user` для демо - email аккаунта Aéza из `DEMO_USER_EMAIL`, пароль хранит Aéza;
- отделы "Офис" (аренда, подписка) и "Инфраструктура" (сервер).

Тестовые данные загружает отдельная команда `uv run python -m app.seed` (в compose - одноразовый запуск), а не флаг при старте: флаг легко забыть включённым на сервере.
