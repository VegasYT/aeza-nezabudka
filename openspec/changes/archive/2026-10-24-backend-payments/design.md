# Design

## Context

Правила сроков, просрочки и итогов уже в `apps/payments/domain.py` (шаг 3), контракт и роли - на месте (шаги 2, 4), журнал - `apps/audit`. Модель данных - `docs/plan.md`, раздел 3, и ADR-003.

## Goals / Non-Goals

**Goals:**

- инварианты в базе: `unique (recurring_payment_id, seq)`, проверки сумм, валют, номеров;
- сервис решает по функциям домена, а не дублирует правила.

**Non-Goals:**

- отделы, напоминания, события, идемпотентность (шаги 6, 8, 9).

## Decisions

### Таблицы

- `recurring_payments`: `id` (uuid), `name`, `amount_minor` (bigint, > 0), `currency` (check `RUB`/`USD`/`EUR`), `period` (check `month`), `anchor_day` (1-31), `schedule_first_due_date`, `schedule_from_seq` (>= 0), `department_id` (uuid, null; внешний ключ добавит шаг 8), `stopped_at`, `created_by_id`, `created_by_login`, `created_at`, `updated_at`.
- `payment_occurrences`: `id`, `recurring_payment_id` (fk), `seq` (>= 0), `due_date`, `amount_minor`, `currency`, `paid_on`, `paid_by_id`, `paid_by_login`, `updated_at`; `unique (recurring_payment_id, seq)`; check: дата оплаты и логин автора заданы вместе; индекс по `due_date`.
- Валюта хранится строкой с check, а не типом enum PostgreSQL: новую валюту проще добавить миграцией.

### Слои

- `repository.py` - запросы SQLAlchemy Core и ORM: выборки со страницами и фильтрами, итоги, вставка периодов `on conflict do nothing`.
- `service.py` - сценарии в одной транзакции: блокировка строки платежа `for update` при изменении и прекращении, решения через функции домена, запись журнала через `apps.audit.service.record` в той же сессии.
- `router.py` - разбор запроса и ответ; "сегодня" из `Clock` приложения.

### Досоздание

`ensure_periods(session, today)` берёт действующие платежи с последним номером периода и вставляет `occurrences_to_create(...)` через `insert ... on conflict do nothing`. Два одновременных вызова не создают дублей благодаря ограничению базы, отдельная блокировка не нужна. Создание и изменение платежа вызывают ту же функцию для одного платежа.

### Ближайший срок

`next_due_date` - минимальный срок неоплаченного периода не раньше сегодня, считается подзапросом в выборке платежей. Решено так, а не "самый ранний неоплаченный вообще": просроченный период показывает список периодов, а у платежа полезнее ближайшая предстоящая оплата.

### Статус и итоги в SQL

Фильтр `overdue` - `paid_on is null and due_date < :today`; итоги - `sum(...) filter (where ...)` по валютам с добавлением отсутствующих валют нулями. Это повторяет правила домена, поэтому тест сверяет итоги API с `domain.summarize` на одних данных.

### Отделы до шага 8

Колонка `department_id` уже есть, но таблицы отделов ещё нет. Переданный `department_id` - 422 "Отдел не найден": отдела с таким идентификатором действительно не существует. Фильтр по отделу работает по колонке и пока возвращает пустой список. `department` в ответах - `null`.

### Фабрика сессий в приложении

`create_app` принимает `session_factory`: тесты API передают фабрику, привязанную к соединению с откатом (`tests/conftest.py`), и данные одного теста не видны другому.

## Risks / Trade-offs

- [Две параллельные правки одного платежа] -> блокировка строки платежа `for update` на время изменения и прекращения.
- [Правила просрочки повторены в SQL] -> тест сравнения итогов API с функцией домена.
