# Design

## Context

Очередь `notifications` хранит получателя строкой: `group` или `sub` пользователя (шаг 6). Отправитель для неизвестного получателя отменяет напоминание. Бот не может написать человеку первым, поэтому привязку начинает пользователь ссылкой из веб-панели (раздел 6 `docs/plan.md`).

## Decisions

### Таблицы

- `telegram_links`: `user_id` (pk, `sub`), `login`, `chat_id` (bigint, unique), `telegram_username`, `personal_enabled` (по умолчанию true), `linked_at`, `blocked_at`.
- `telegram_link_codes`: `code_hash` (pk, sha256 кода), `user_id`, `login`, `expires_at`, `used_at`. В базе только хеш: утечка таблицы не даёт привязать чужой аккаунт.

Внешних ключей на пользователей нет: пользователи живут в Keycloak.

### Ссылка привязки

Код - `secrets.token_urlsafe(24)` (32 символа из алфавита, который Telegram допускает в параметре `start`). Новая ссылка удаляет прежние неиспользованные коды пользователя. Ссылка `https://t.me/<бот>?start=<код>`: имя бота `api` узнаёт через `getMe` при первом запросе и запоминает. Без `TELEGRAM_BOT_TOKEN` - 409 `telegram_not_configured`; если Telegram не ответил - 503 `telegram_unavailable` (как и `identity_unavailable`, в контракте не описывается).

### Команды бота

Обрабатываются только сообщения из личных чатов (`chat.type == "private"`):

- `/start <код>`: код найден, не использован и не просрочен - код помечается использованным, привязка пользователя создаётся или заменяется (новый чат, `personal_enabled = true`, `blocked_at = null`). Если этот чат был привязан к другому пользователю, та привязка удаляется: `chat_id` уникален. Ответ "Готово...".
- `/start` без кода из привязанного чата - снимает `blocked_at` (пользователь разблокировал бота и снова его запустил).
- `/stop` - удаляет привязку этого чата, отменяет ожидающие личные напоминания.
- иначе, в том числе неверный, просроченный или использованный код - подсказка "откройте ссылку из веб-панели", ничего не меняется.

Ответ бота отправляется после коммита обработки. Сбой ответа не откатывает привязку.

### Чтение обновлений

Задача `telegram_updates` в `worker`: держит отдельное соединение с `pg_try_advisory_lock(<ключ>)`. Пока блокировку держит другой экземпляр, задача только пробует её взять раз в секунду. Владелец блокировки вызывает `getUpdates(offset, timeout=10)` и обрабатывает сообщения по одному. Смещение хранится в памяти: после перезапуска Telegram повторит неподтверждённые обновления, повторный `/start` с уже использованным кодом получит подсказку, привязка не пострадает. Перед каждым опросом соединение проверяется запросом `select 1`, при обрыве блокировка считается потерянной.

### Получатели

Постановка объединяет общий чат (если задан) и `select user_id::text from telegram_links where personal_enabled and blocked_at is null`. Отправитель для личного получателя берёт `chat_id` из привязки в той же транзакции; нет привязки, выключено или заблокировано - `cancelled`. `ChatBlocked` для личного получателя ставит `blocked_at` и переводит напоминание в `failed`.

Выключение личных напоминаний и отвязка сразу отменяют ожидающие напоминания пользователя. Повторное включение не возвращает отменённые: `unique` не пустит новую строку для того же периода. Это то же допущение, что и для повторной отметки оплаты.

### Связь модулей

`users.service` вызывает `reminders.service.forget_user` перед удалением в Keycloak: если удаление в Keycloak не удастся, пользователь просто привяжет Telegram заново, а обратный порядок оставил бы рассылку удалённому пользователю.

### Протоколы

`Notifier` (отправка) из шага 6 остаётся, рядом `BotUpdates`: `username()` и `get_updates(offset, timeout)`, возвращающий `IncomingMessage(update_id, chat_id, chat_type, username, text)`. `TelegramNotifier` реализует оба. `api` создаёт его по настройкам и закрывает при остановке.
