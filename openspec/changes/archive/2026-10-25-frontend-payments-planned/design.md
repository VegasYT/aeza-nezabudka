# Design

## Context

Мотивация - в proposal.md. Строится на `frontend-payments-views`: `useAllPages` и `useCalendarData` (`model/views-queries.ts`), запись календаря `CalendarEntry` и `plannedAppearsOn` (`lib/calendar.ts`), значок `PlannedMark`, `SummaryCards` со сложением `plannedMinor`/`plannedCount`. Список таблицы - серверные страницы по 50 (`occurrencesOptions`, `page` в адресе), на телефоне - «Показать ещё» по 20 (`usePhoneOccurrences`). `GET /payments/forecast` возвращает плановые периоды по сроку (`from` по умолчанию сегодня, `to` обязателен, диапазон не больше двух лет, без валюты и статуса).

## Decisions

### Запрос плановых периодов

`usePlannedPeriods(search, period, enabled)`: все страницы `forecast` за [max(начало периода, сегодня), конец периода], отдел - параметром, валюта - в браузере. Без конца периода, при статусе «Просрочено» или «Оплачено» и в календаре и бюджете запрос не идёт. Диапазон больше двух лет обрезается до двух лет от начала: дальше сервер ответит 400, а такой период на экране - исключение.

### Плановые на странице: границы по соседним созданным

Плановые встают на страницу по сроку, а не в конец списка. Для страницы `k` при порядке «сначала ранние» берутся плановые со сроком в (последний срок страницы `k-1`; последний срок страницы `k`]; у первой страницы нет нижней границы, у последней - верхней. При порядке «сначала поздние» - зеркально. Последний срок предыдущей страницы даёт отдельный запрос `limit=1` со смещением `(k-1)*50-1` с теми же фильтрами; он нужен только со второй страницы и если есть плановые. На телефоне при догрузке: плановые не дальше последнего загруженного срока, пока есть следующая порция, и все - когда загружено всё. Внутри страницы созданные и плановые сортируются по сроку; при одинаковом сроке созданный идёт первым. Правила - чистые функции `lib/planned.ts` с табличным тестом.

Альтернатива - плановые отдельным блоком под таблицей. Отвергнута: макет `ExtraTotals` показывает их в общем порядке по сроку, а «На дату» и сортировка теряли бы смысл.

### Строки и карточки

`OccurrencesTable` и `OccurrenceCards` принимают общий список записей (`CalendarEntry`): созданные рисуются как раньше, плановые - приглушённым названием и суммой, «По расписанию» с `PlannedMark`, подписью «появится <дата>» (или «срок через N дней», если предыдущего периода нет в выборке), прочерками и без действий. Подпись под таблицей: «Показаны 1–6 из 6, ещё 2 по расписанию»; без созданных - «2 периода по расписанию».

### Итоги

`summaryOptions` добавляет `includePlanned`, если у периода есть конец. Строка о прошлой просрочке не меняется: плановые периоды не бывают в прошлом.

### Тесты

`servePaymentsScreen` отвечает пустым прогнозом, чтобы прежние тесты не получали необработанный запрос. Новые сценарии - в `src/app/payments-views.test.tsx`; распределение по страницам - табличный тест `lib/planned.test.ts`.

## Risks / Trade-offs

- [Лишний запрос границы страницы] → только со второй страницы и при наличии плановых, `limit=1`.
- [Число строк на странице больше 50] → допустимо: плановых обычно единицы; подпись говорит, сколько их.
