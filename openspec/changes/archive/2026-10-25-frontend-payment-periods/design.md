# Design

## Context

- Форма платежа и расчёты расписания живут в `pages/recurring-payments` (`ui/payment-form-dialog.tsx`, `model/schedule.ts`, `model/payment-view.ts`). Экран «Платежи» не может импортировать их из чужой страницы (FSD).
- Расписание считается только для месяца: `nextDueAfter(date, anchorDay)`, `scheduleLabel(anchorDay)`, `dueDayHint(anchorDay)`.
- Контракт: `period` - `day | week | month | year`, `periodCount` 1-366 (обязателен в ответе, необязателен при создании, оба поля необязательны в `PATCH`). Месяц и год считаются от якорного дня с обрезкой до конца месяца, день и неделя - равными шагами (`openspec/specs/payment-schedule`).

## Goals / Non-Goals

**Goals:**
- Одна форма платежа на обе страницы.
- Подписи периодичности без неверных падежей при любом N.

**Non-Goals:**
- Свой компонент выбора периода: хватает `Select`, `NumberInput` и `Select` единицы.

## Decisions

1. **Слайсы.**
   - `entities/recurring-payment`: расписание (`nextDueAfter`, подписи периодичности и расписания, следующие сроки, сдвиг короткого месяца), подписи платежа (`nextDueView`, метка просрочки, названия валют) и `useRefreshRecurring`.
   - `features/recurring-payment-form`: `PaymentFormDialog`.
   - Окно прекращения и метки списка остаются в странице, ими пользуется только она.
   
   Альтернатива - виджет. FSD 2.1 советует виджеты только для крупных самостоятельных блоков, а создание платежа - действие пользователя, то есть фича.
2. **Выбор периодичности.**
   - `Select` с готовыми вариантами (месяц 1, 3, 6; год 1; неделя 1, 2) и «Другая периодичность».
   - Своя периодичность - `NumberInput` 1-366 и `Select` единицы, подписанные «Раз в»: «10 дней», «3 месяца», «21 неделю».
   - Платёж с сочетанием не из списка открывается сразу на «Другой периодичности».
   - Значение формы - пара `period` и `periodCount`, выбор варианта её только заполняет.
3. **Подписи.**
   - Для N = 1 и известных сочетаний - слова: «ежемесячно», «раз в квартал», «раз в полгода», «ежегодно», «еженедельно», «раз в две недели», «ежедневно».
   - Иначе «раз в N <единица в винительном падеже>» через `plural`: «раз в 21 день», «раз в 2 недели», «раз в 5 лет». Так не нужен «каждый/каждые», который зависит от числа.
   - Привязка срока берётся из якорного дня (месяц) или ближайшего срока (год - «5 ноября», неделя - «по понедельникам»). У прекращённого платежа без ближайшего срока - только периодичность.
4. **Подсказка под датой - два следующих срока.** Они считаются тем же `nextDueAfter`. Одинаково работают для всех единиц и сами показывают сдвиг на конец короткого месяца. Прежняя фраза «Срок каждый месяц 26-го числа» умела только месяц.
5. **Изменение.**
   - `period` и `periodCount` сравниваются с платежом по отдельности, в `PATCH` уходит только то, что изменилось.
   - Пояснение про якорь 29-31 показывается, если `shortMonthDue` нашёл сдвинутый срок за 24 шага расписания. Для года с 31 января его нет, и пояснения нет.
6. **«Платежи».**
   - Шапка получает проп `onAdd`, только для администратора (`useCurrentUser`). На телефоне - `ActionIcon` 44 px с доступным именем «Добавить платёж» рядом с фильтрами.
   - Пустое состояние администратора - кнопка вместо ссылки на раздел.
   - Перечитывание после создания уже делает `useRefreshRecurring` (периоды и итоги в его списке).

## Risks / Trade-offs

- [Год без ближайшего срока (прекращён или оплачен заранее)] → в подписи нет даты, только «ежегодно». Точная дата видна в истории карточки.
- [Перенос файлов между слайсами] → поведение «Регулярных платежей» не меняется, его закрывают существующие тесты раздела.
