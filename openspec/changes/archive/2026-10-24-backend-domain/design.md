# Design

## Context

Модули `apps/payments` и `apps/reminders` пока содержат только роутеры и схемы контракта. Правила из `docs/plan.md` (раздел 4) и ADR-003, ADR-004, ADR-006, ADR-007 здесь становятся кодом. Сервисы шагов 5, 6 и 9 будут вызывать эти функции, поэтому их входы - простые значения, не модели базы и не схемы API.

## Goals / Non-Goals

**Goals:**

- все правила с датами - чистые функции от "сегодня" и данных периода, проверяемые таблицами без базы.

**Non-Goals:**

- хранение, транзакции, планировщик и доставка: их делают шаги 5, 6, 9.

## Decisions

### Где живут правила

- `apps/payments/domain.py`: расписание, досоздание, влияние изменения и прекращения, проверка дат, просрочка, итоги.
- `apps/reminders/domain.py`: два предиката окна напоминания. Модуль `reminders` вызывает `payments` только через его сервис (`backend/AGENTS.md`), но доменные типы периода нужны обоим. Чтобы не нарушить правило импорта, предикаты `reminders` принимают простые значения (срок, дата оплаты, действует ли платёж), а не тип из `payments`.

### Типы

Неизменяемые `dataclass(frozen=True)`:

- `Schedule(anchor_day, first_due_date, from_seq)` - отрезок расписания (ADR-003); `Schedule.starting(next_due_date, from_seq)` берёт якорный день из даты.
- `PlannedOccurrence(seq, due_date)` - период, который нужно создать.
- `OccurrenceState(seq, due_date, paid_on, amount_minor, currency)` - то, что домену нужно знать о существующем периоде.
- `CurrencyTotals` и функция итогов возвращают значения для всех трёх валют в фиксированном порядке RUB, USD, EUR.

Валюта - `Currency` из `apps/payments/schemas.py` уже есть; домен её переиспользует, чтобы не завести второе перечисление тех же значений. Это единственная связь домена со схемами контракта, другие типы схем домен не импортирует.

### Расчёт срока

`due_date(schedule, seq)`: номер месяца `first_due_date` плюс `seq - from_seq`, затем `min(anchor_day, последний день месяца)` через `calendar.monthrange`. Стандартная библиотека, без `dateutil`: нужна одна операция, и её поведение на 31-м числе явно задано тестами.

### Досоздание

`occurrences_to_create(schedule, last_seq, today)` возвращает периоды с номерами после `last_seq` (или с `from_seq`, если периодов отрезка нет), пока срок не станет позже сегодня, включая первый такой. Если последний существующий период уже позже сегодня, список пустой. Функция не знает про базу: защита от дублей при гонке - `unique (recurring_payment_id, seq)` на шаге 5.

### Изменение и прекращение

- `is_replaceable(state, today)`: не оплачен и срок сегодня или позже. По нему выбираются периоды для новой суммы и валюты и для замены при новом расписании.
- `next_segment_from_seq(remaining)`: последний оставшийся номер плюс 1 или 0.
- `removed_on_stop(state, today)`: не оплачен и срок позже сегодня.

Граница для изменения (сегодня включительно) и прекращения (строго позже сегодня) разная намеренно: период со сроком сегодня при прекращении остаётся долгом, а при изменении даты заменяется новым расписанием, чтобы не появилось двух обязательств на одну дату.

### Ошибки проверки дат

Проверки возвращают текст ошибки на русском или `None` (`next_due_date_error`, `paid_on_error`). Сервис шага 5 превращает текст в `AppError` 422 с полем. Альтернатива - бросать исключение из домена - связала бы домен с форматом ошибок API.

### Просрочка

`overdue_days(due_date, paid_on, today)`: для неоплаченного `max(0, today - due)`, для оплаченного `max(0, paid_on - due)`. `is_overdue` - это `overdue_days > 0`. Одна функция даёт и флаг, и число для ответа API.

### Итоги

`summarize(states, today)` суммирует по валютам: `unpaid` - без даты оплаты, `overdue` - неоплаченные с просрочкой; оплаченные с опозданием в `overdue` не входят, потому что поле означает долг, который ещё висит.

## Risks / Trade-offs

- [Правила понадобятся в SQL: фильтр "просрочен" и итоги считаются в базе для больших списков] -> на шаге 5 запросы повторяют эти правила, а тесты сверяют результат запроса с функцией домена на одних и тех же данных.
