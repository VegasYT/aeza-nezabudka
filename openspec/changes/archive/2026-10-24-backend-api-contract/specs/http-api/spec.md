# Spec Delta

## Purpose

Опубликованный контракт REST API Invoice Keeper: какие эндпоинты есть, в каком формате они принимают и отдают данные и как описаны ошибки и безопасность. По нему работают frontend, внешние системы и жюри в Swagger.

## ADDED Requirements

### Requirement: Контракт совпадает с кодом
Файл `backend/api/openapi.yaml` SHALL совпадать со схемой OpenAPI, которую строит приложение, и SHALL обновляться только выгрузкой из приложения.

#### Scenario: Файл актуален
- **WHEN** схема приложения и файл `backend/api/openapi.yaml` сравниваются
- **THEN** они совпадают

#### Scenario: Схема изменилась, файл нет
- **WHEN** в приложении изменилась схема операции, а файл не выгружен заново
- **THEN** проверка несовпадения не проходит и называет расхождение

### Requirement: Состав эндпоинтов
Контракт SHALL содержать операции под `/api/v1`: `GET /auth/me`; `GET`, `POST /recurring-payments`; `GET`, `PATCH`, `DELETE /recurring-payments/{id}`; `GET /payment-occurrences`; `GET`, `PATCH /payment-occurrences/{id}`; `GET /payments/summary`; `GET`, `POST /users`; `PATCH`, `DELETE /users/{id}`; `GET`, `POST /departments`; `PATCH`, `DELETE /departments/{id}`; `GET`, `PATCH`, `DELETE /me/telegram`; `POST /me/telegram/link`.

#### Scenario: Все операции на месте
- **WHEN** клиент читает `/api/v1/openapi.json`
- **THEN** в нём есть каждая перечисленная операция с описанием на русском

### Requirement: Общие соглашения формата
Тела запросов и ответов SHALL быть JSON с именами полей в snake_case. Идентификаторы SHALL быть UUID. Суммы SHALL передаваться целым числом в минимальных единицах валюты (`amount_minor`) вместе с кодом валюты `RUB`, `USD` или `EUR`. Даты без времени SHALL иметь формат `ГГГГ-ММ-ДД`, моменты времени - ISO 8601 с часовым поясом.

#### Scenario: Сумма и валюта
- **WHEN** контракт описывает сумму платежа
- **THEN** это целое поле `amount_minor` и поле `currency` со значениями `RUB`, `USD`, `EUR`

#### Scenario: Срок оплаты
- **WHEN** контракт описывает срок или дату оплаты
- **THEN** это строка в формате даты без времени

### Requirement: Списки с пагинацией
Каждая операция, которая возвращает список, SHALL отвечать объектом `items`, `total`, `limit`, `offset` и принимать параметры `limit` (от 1 до 100, по умолчанию 50) и `offset` (от 0, по умолчанию 0).

#### Scenario: Параметры по умолчанию
- **WHEN** клиент запрашивает список без `limit` и `offset`
- **THEN** контракт задаёт `limit` 50 и `offset` 0

#### Scenario: Слишком большая страница
- **WHEN** клиент передаёт `limit=500`
- **THEN** ответ 422, в `fields` указано поле `limit`

### Requirement: Ошибки описаны в контракте
Каждая операция SHALL описывать в контракте ответы с ошибками в общем формате: 401 для операций с авторизацией, 403 для операций только администратора, 404 для операций с `{id}`, 409 там, где операция невозможна в текущем состоянии, и 422 для операций с параметрами или телом.

#### Scenario: Операция администратора
- **WHEN** клиент читает описание `POST /recurring-payments`
- **THEN** в нём есть ответы 401, 403 и 422 со схемой общего формата ошибок

### Requirement: Безопасность в контракте
Контракт SHALL описывать схему безопасности OAuth2 с потоками Authorization Code (PKCE) и client credentials через Keycloak на том же домене, и каждая операция `/api/v1`, кроме документации, SHALL ссылаться на неё. Swagger SHALL входить через Keycloak кнопкой Authorize.

#### Scenario: Операция требует авторизации
- **WHEN** клиент читает описание любой операции `/api/v1`
- **THEN** у операции указана схема безопасности OAuth2

#### Scenario: Вход из Swagger
- **WHEN** пользователь нажимает Authorize в `/api/v1/docs`
- **THEN** Swagger предлагает вход через Keycloak с PKCE и после входа отправляет токен в запросах

### Requirement: Ключ идемпотентности при создании платежа
Контракт `POST /recurring-payments` SHALL принимать необязательный заголовок `Idempotency-Key` (от 1 до 128 символов).

#### Scenario: Заголовок описан
- **WHEN** клиент читает описание `POST /recurring-payments`
- **THEN** в нём есть необязательный заголовок `Idempotency-Key`

### Requirement: Ещё не реализованные операции
Пока логика операции не реализована, операция SHALL отвечать 501 с кодом `not_implemented` и текстом на русском в общем формате ошибок, после проверки параметров и тела по контракту.

#### Scenario: Корректный запрос
- **WHEN** клиент вызывает нереализованную операцию с корректными параметрами
- **THEN** ответ 501 `{"code": "not_implemented", "message": "Операция ещё не реализована"}`

#### Scenario: Некорректный запрос
- **WHEN** клиент вызывает нереализованную операцию с телом, которое не проходит проверку
- **THEN** ответ 422 с `fields`, а не 501
