# Proposal

## Why

Критерии приёмки кейса: без авторизации панель и данные недоступны, пользователь не выполнит действия администратора даже через API, администратор задаётся в `.env`, а пользователей заводит администратор. Сейчас контракт только описывает схему безопасности, токен не проверяется, а `/auth/me` и `/users` отвечают 501. Шаг 4 `backend/plan.md` делает вход через Keycloak (ADR-008) и управление пользователями (ADR-005) настоящими; от этого зависят все следующие шаги с данными.

## What Changes

- Проверка токена Keycloak на каждой операции `/api/v1`: подпись по ключам JWKS, издатель, аудитория `api`, срок. Без корректного токена - 401.
- Роли из токена (`admin`, `user`, `integration`) и проверка роли у операций администратора - 403. Нереализованные операции теперь сначала проверяют токен и роль, потом отвечают 501.
- `GET /auth/me` по токену.
- `/users` через Admin API Keycloak: список обычных пользователей, создание с ролью `user`, смена пароля, отключение и включение, удаление; завершение сессий при смене пароля, отключении и удалении; 409 для администратора и занятого логина.
- Синхронизация администратора из `ADMIN_LOGIN` и `ADMIN_PASSWORD` при старте `api`; `/readyz` ждёт её.
- Журнал действий: таблица `audit_log` и записи об операциях с пользователями.
- `infra/keycloak/realm.json`: realm `invoice-keeper`, роли, клиенты `web` и `backend`, аудитория `api`, защита от перебора, политика паролей, необязательные почта и имя, русский язык страницы входа. Импортируется только при первом старте.
- `infra/keycloak/configure.sh`: при каждом запуске приводит настройки, зависящие от окружения (адрес сайта у клиента `web`, секрет клиента `backend`), к значениям из окружения; пользователей не трогает.
- Новые переменные окружения `api` для Keycloak и администратора.

Вне изменения:

- `infra/compose.yaml` и публикация Keycloak через Caddy по `/auth` (общий этап "Фундамент"); поэтому вход из Swagger руками проверяется после него;
- сервисные учётные записи внешних систем с ролью `integration` (шаг 9): здесь роль только распознаётся;
- вход через AD или LDAP (настройка, шаг 9).

## Capabilities

### New Capabilities

- `authentication`: проверка токена, ответ 401, текущий пользователь и его роль.
- `authorization`: какие роли могут выполнять какие операции, ответ 403.
- `user-management`: пользователи через Keycloak, администратор из `.env`, завершение сессий.
- `audit-log`: журнал действий с автором и временем.

### Modified Capabilities

- `backend-platform`: готовность `api` учитывает синхронизацию администратора с Keycloak.
- `http-api`: нереализованные операции отвечают 501 только после проверки токена и роли.

## Impact

- `backend/`: `core/auth.py` (проверка токена и роли), `core/config.py` (настройки Keycloak и администратора), модули `apps/users` (сервис и Keycloak) и `apps/audit` (новый), миграция `audit_log`, зависимости PyJWT с криптографией, python-keycloak, httpx в основные.
- `infra/keycloak/realm.json` и `infra/keycloak/configure.sh` (новая папка `infra/`); подключение скрипта одноразовым шагом в compose - на этапе "Фундамент".
- Контракт `backend/api/openapi.yaml` меняется только в описаниях, поля и коды те же; frontend затронут поведением: без токена теперь 401, без роли администратора - 403.
- `backend/AGENTS.md` (переменные), `backend/plan.md` (статус шага 4).
- Интеграционным тестам нужен Docker: PostgreSQL и Keycloak в контейнерах.
