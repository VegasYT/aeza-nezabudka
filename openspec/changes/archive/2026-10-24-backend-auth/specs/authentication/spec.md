# Spec Delta

## Purpose

Как API узнаёт, кто делает запрос: проверка токена Keycloak, отказ без корректного токена и данные текущего пользователя.

## ADDED Requirements

### Requirement: Проверка токена
Каждая операция `/api/v1` SHALL принимать только токен доступа Keycloak в заголовке `Authorization: Bearer`, подписанный ключом realm `invoice-keeper`, выданный издателем из настроек, с аудиторией `api` и не истёкший. Иначе SHALL быть ответ 401 `unauthorized` в общем формате ошибок с заголовком `WWW-Authenticate: Bearer`. Документация и проверки `/healthz`, `/readyz` токена не требуют.

#### Scenario: Без токена
- **WHEN** клиент вызывает операцию `/api/v1` без заголовка `Authorization`
- **THEN** ответ 401 с кодом `unauthorized`

#### Scenario: Истёкший токен
- **WHEN** срок токена прошёл
- **THEN** ответ 401

#### Scenario: Чужой издатель или аудитория
- **WHEN** токен выдан другим издателем или без аудитории `api`
- **THEN** ответ 401

#### Scenario: Поддельная подпись
- **WHEN** токен подписан не ключом realm
- **THEN** ответ 401

#### Scenario: Документация без токена
- **WHEN** клиент открывает `/api/v1/docs` без токена
- **THEN** ответ 200

### Requirement: Роль из токена
Роль запроса SHALL определяться по ролям realm в токене: `admin`, если есть роль `admin`; иначе `integration`, если есть роль `integration`; иначе `user`, если есть роль `user`. Токен без этих ролей SHALL получать 403 `forbidden` на любой операции.

#### Scenario: Администратор
- **WHEN** в токене роли `admin` и `user`
- **THEN** роль запроса - `admin`

#### Scenario: Нет ролей системы
- **WHEN** в токене нет ролей `admin`, `integration` и `user`
- **THEN** ответ 403 на любую операцию `/api/v1`

### Requirement: Текущий пользователь
`GET /auth/me` SHALL возвращать идентификатор пользователя Keycloak, логин и роль из токена.

#### Scenario: Пользователь вошёл
- **WHEN** пользователь `buh.petrova` с ролью `user` запрашивает `GET /auth/me`
- **THEN** ответ 200 с его идентификатором, логином `buh.petrova` и ролью `user`

### Requirement: Ключи подписи без обращения на каждый запрос
Ключи подписи realm SHALL кешироваться; при недоступном Keycloak уже выданные корректные токены SHALL проходить проверку, пока ключи в кеше. Токен с неизвестным ключом SHALL приводить к повторному чтению ключей, не чаще раза в 30 секунд.

#### Scenario: Keycloak недоступен
- **WHEN** ключи уже прочитаны, Keycloak стал недоступен, клиент присылает действующий токен
- **THEN** операция выполняется

#### Scenario: Ключи нельзя прочитать
- **WHEN** ключи ещё не прочитаны и Keycloak недоступен
- **THEN** ответ 503 `identity_unavailable`
