# Design

## Context

Есть каркас `api`, контракт с заглушками и схема безопасности OAuth2 с `auto_error=False` (`core/security.py`): сейчас токен не проверяется. Решения о входе приняты в ADR-005 и ADR-008, `docs/plan.md` (раздел 5). Keycloak 26.8.1 (`quay.io/keycloak/keycloak:26.8.1`), realm `invoice-keeper` зафиксирован в контракте. Compose ещё нет, поэтому интеграционные тесты сами поднимают Keycloak в контейнере с тем же `realm.json`.

## Goals / Non-Goals

**Goals:**

- проверка токена и ролей одна на все операции, новые модули получают её объявлением роли у операции;
- быстрые тесты без Keycloak (фейки) и интеграционные с настоящим Keycloak на сценариях входа и пользователей.

**Non-Goals:**

- выдача токенов и страница входа: это Keycloak; публикация Keycloak через Caddy - этап "Фундамент".

## Decisions

### Настройки

Отдельный класс `IdentitySettings` в `core/config.py`, его читает только `api`: `worker` и миграциям Keycloak не нужен, и их запуск не должен требовать лишних переменных.

- `KEYCLOAK_PUBLIC_URL` - адрес, по которому Keycloak видит браузер; издатель токена - `<public>/realms/invoice-keeper`.
- `KEYCLOAK_INTERNAL_URL` - адрес для ключей JWKS и Admin API внутри сети; по умолчанию равен публичному.
- `KEYCLOAK_AUDIENCE` (по умолчанию `api`), `KEYCLOAK_BACKEND_CLIENT_ID` (по умолчанию `backend`), `KEYCLOAK_BACKEND_CLIENT_SECRET`.
- `ADMIN_LOGIN`, `ADMIN_PASSWORD`.

Секреты - `SecretStr`, ошибки конфигурации - как в `backend-platform`.

### Проверка токена: `core/auth.py`

- `TokenVerifier`: ключи JWKS читаются через httpx с `<internal>/realms/invoice-keeper/protocol/openid-connect/certs` и кешируются в памяти процесса. Неизвестный `kid` - повторное чтение, не чаще раза в 30 секунд (защита от перебора поддельных `kid`). PyJWT: алгоритм только `RS256`, обязательные `exp`, `iss`, `aud`, допуск по часам 30 секунд.
- `Principal(id, login, role)`: `id` из `sub`, логин из `preferred_username`, роль по правилу из спецификации.
- Зависимости FastAPI: `current_principal` (на роутере `/api/v1`, вместо прежней пустой зависимости) и `require_roles(*roles)` у операций. FastAPI решает зависимости раньше, чем выбрасывает ошибки проверки тела, поэтому порядок ответов 401, 403, затем 422 получается сам. Проверка роли идёт до обработчика, поэтому 403 приходит раньше 404.
- 401 - `AppError` с заголовком `WWW-Authenticate: Bearer`: `AppError` получает необязательные заголовки.
- Наборы ролей в одном месте `core/auth.py`: `ADMIN`, `STAFF` (`admin`, `user`), `STAFF_AND_INTEGRATION`. Матрица:

| Операции | Роли |
| --- | --- |
| `GET /auth/me` | все три |
| чтение и запись платежей, периодов, итоги, `GET /departments` | `STAFF_AND_INTEGRATION`, кроме записи платежей - `ADMIN` и `integration` |
| `/users`, запись отделов | `ADMIN` |
| `/me/telegram` | `STAFF` |

Создание, изменение и прекращение платежа доступны `admin` и `integration`: внешняя система заводит платежи (ADR-011), а обычный пользователь - нет.

### Пользователи: `apps/users`

- `IdentityProvider` (протокол в `apps/users/service.py`): список пользователей роли `user`, получение пользователя с ролями, создание, смена пароля, включение и отключение, удаление, завершение сессий, синхронизация администратора. Реализации: `KeycloakIdentityProvider` (`apps/users/keycloak.py`, python-keycloak, асинхронные методы `a_*`, клиент `backend` по client credentials) и фейк в памяти для тестов.
- Ошибки Keycloak переводятся на границе реализации: 404 - `UserNotFound`, 409 - `LoginTaken`, 400 с нарушением политики паролей - `PasswordRejected` с текстом, сетевые ошибки и 5xx - `IdentityUnavailable`. Сервис превращает их в `AppError` с кодами из спецификации.
- Список: участники роли `user` без участников роли `admin`, сортировка по логину и пагинация в памяти. Предел - сотни пользователей; при росте - запрос к Keycloak со страницами (`ponytail`-комментарий в коде).
- Создание: пользователь включён, пароль не временный, обязательных действий нет, роль `user` назначается явно (не полагаемся на роль по умолчанию).
- Защита администратора: перед изменением и удалением сервис читает роли пользователя; `admin` - 409.
- Смена пароля и отключение вызывают завершение всех сессий пользователя (`logout` в Admin API).

### Синхронизация администратора

В `lifespan` `api` запускается фоновая задача: пытается синхронизировать администратора, при ошибке ждёт от 1 до 30 секунд с удвоением и повторяет. Флаг `app.state.identity_ready` ставится после успеха; `/readyz` проверяет его последним (`identity_not_ready`). Синхронизация: найти пользователя с точным логином, создать при отсутствии, включить, поставить пароль, назначить `admin` и атрибут `env_managed=true`; найти других пользователей с `env_managed=true` и отключить их, сняв `admin`. Атрибут хранится как неуправляемый: в профиле пользователя realm для этого включена политика `ADMIN_EDIT`.

### Журнал: `apps/audit`

Таблица `audit_log` (`id`, `at`, `actor_id`, `actor_login`, `action`, `entity`, `entity_id`, `details` jsonb) и функция `record(session, principal, action, entity, entity_id, details)`. Операции с пользователями идут во внешнюю систему, поэтому запись журнала делается после успешного ответа Keycloak в отдельной транзакции; при сбое записи операция не откатывается, ошибка пишется в журнал процесса. Для операций с данными в базе (шаги 5-9) запись будет в той же транзакции, что и изменение.

### `infra/keycloak/realm.json`

- realm `invoice-keeper`; роли `admin`, `user`, `integration`; роль `user` входит в роли по умолчанию, чтобы сотрудник, вошедший через AD или LDAP, получал её сам.
- клиент `web`: публичный, только Authorization Code с PKCE S256, `rootUrl` из `${WEB_PUBLIC_URL}`, адреса возврата `/*` относительно него, аудитория `api` через audience mapper.
- клиент `backend`: конфиденциальный, секрет `${KEYCLOAK_BACKEND_CLIENT_SECRET}` (подстановка из окружения при импорте), только сервисная учётная запись с ролями `manage-users`, `view-users`, `query-users`, `view-realm` клиента `realm-management`.
- защита от перебора с временной блокировкой, политика паролей `length(8) and notUsername`, access token 5 минут, сессия 8 часов без активности и не дольше 7 суток, журнал событий входа, русский язык по умолчанию.
- профиль пользователя: почта, имя и фамилия необязательны; неуправляемые атрибуты разрешены администратору (`ADMIN_EDIT`).

### Настройки окружения при каждом запуске: `configure.sh`

`--import-realm` пропускает существующий realm, а данные Keycloak хранятся в PostgreSQL и переживают перезапуск. Поэтому правка `realm.json` или смена `WEB_PUBLIC_URL` и `KEYCLOAK_BACKEND_CLIENT_SECRET` на работающий стенд сама не попадает, и вход ломается без понятной ошибки.

Разделение:

- `realm.json` - структура, применяется один раз: роли, клиенты, профиль пользователя, политики, сроки токенов;
- `configure.sh` - идемпотентный скрипт на `kcadm.sh` из того же образа Keycloak; входит в master realm учётной записью начального администратора Keycloak и выставляет у клиента `web` `rootUrl`, адреса возврата и `webOrigins` из `WEB_PUBLIC_URL`, у клиента `backend` - секрет из `KEYCLOAK_BACKEND_CLIENT_SECRET`. Пользователей и их роли не трогает. В compose он станет одноразовым шагом после готовности Keycloak и до старта `api` (этап "Фундамент"); шаг 9 добавит в него клиентов интеграций.

Структурная правка `realm.json` на стенде с данными (новая роль, новый клиент) переносится тоже через `configure.sh` или консоль Keycloak; пересоздание realm удаляет пользователей и допустимо только осознанно. Это записывается в `backend/AGENTS.md`.

Альтернатива - keycloak-config-cli, который применяет весь `realm.json` декларативно при каждом запуске. Отклонена: ещё один образ и свой формат ради двух-трёх настроек; в Goden такой же скрипт на `kcadm.sh` работал.

### Тесты

- Быстрые: RSA-ключ генерируется в тесте, токены подписываются им, JWKS отдаёт `httpx.MockTransport`; фейковый `IdentityProvider`. Контрактный тест заглушек получает токен администратора, матрица ролей проверяется отдельным тестом по всем операциям.
- Интеграционные: Keycloak 26.8.1 в контейнере (`start-dev --import-realm`, папка `infra/keycloak` смонтирована в `/opt/keycloak/data/import`) на сессию тестов. Для получения токенов пользователей фикстура создаёт через Admin API тестовый клиент с Direct Access Grants: в `realm.json` такого клиента нет.

## Risks / Trade-offs

- [Профиль пользователя Keycloak 26 требует почту и имя, и вход падает с "Account is not fully set up"] -> профиль в `realm.json` и интеграционный тест входа нового пользователя.
- [Keycloak в тестах стартует 20-40 секунд] -> один контейнер на сессию, тесты помечены `integration`, быстрые тесты от него не зависят.
- [Сбой записи журнала после успешной операции в Keycloak] -> операция не откатывается; запись журнала для внешних операций - лучшая попытка, это сказано в спецификации неявно и здесь явно.
- [Правка `realm.json` не доходит до стенда с данными] -> настройки окружения применяет `configure.sh` при каждом запуске, структурные правки - через него же или консоль; правило в `backend/AGENTS.md`.
- [Издатель токена зависит от адреса Keycloak] -> `KEYCLOAK_PUBLIC_URL` задаётся явно; в compose Keycloak получит `KC_HOSTNAME` с тем же адресом (этап "Фундамент").
