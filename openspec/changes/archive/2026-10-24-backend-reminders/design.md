# Design

## Context

Периоды создаёт `PaymentsService` в транзакциях API (шаг 5), правила "период подходит для напоминания" - чистые функции `apps/reminders/domain.py` (шаг 3). Процесс `worker` умеет крутить `PeriodicJob` с корректной остановкой (шаг 1), но задач у него нет. Модули обращаются друг к другу только через `service.py`.

## Goals / Non-Goals

**Goals:** одно сообщение на период и вид даже при двух экземплярах `worker`; поздний платёж получает напоминание без ожидания тика; временные ошибки Telegram не теряют напоминание.

**Non-Goals:** личные чаты (шаг 7), метрики (шаг 10), точное соблюдение лимитов Telegram между несколькими экземплярами.

## Decisions

### Зависимость модулей

`reminders` зависит от `payments`: напоминает о его периодах. `payments.service` даёт две функции, работающие в чужой сессии:

- `open_occurrence_ids(due_from, due_to, payment_ids=None)` - запрос `select` неоплаченных периодов действующих платежей со сроком в границах; окна `due_soon` и `overdue` из него строит `reminders`, так правила напоминаний остаются в одном модуле;
- `occurrence_subjects(session, occurrence_ids)` - данные для повторной проверки и текста: название, сумма, валюта, срок, оплачен ли, действует ли платёж.

Обратный вызов из `payments` в `reminders` дал бы цикл импортов. Поэтому `PaymentsService` принимает необязательный `after_change(session, today, payment_ids)` и вызывает его в транзакции создания и изменения после досоздания периодов. Связывает модули `app/main.py`. Альтернатива - ждать тика - задерживает напоминание о позднем платеже до минуты и расходится с ADR-004.

### Таблица notifications

`id` (uuid, `gen_random_uuid()` в базе: строки вставляет `insert ... select`), `occurrence_id` (fk, `on delete cascade`: прекращение удаляет будущие периоды вместе с их напоминаниями), `kind`, `channel` (`telegram`), `recipient` (`group` или `sub` пользователя - шаг 7), `state`, `attempts`, `next_attempt_at`, `last_error`, `sent_at`, `external_id`, `created_at`. `unique (occurrence_id, kind, channel, recipient)`, `check` на значения `kind` и `state`, частичный индекс `(next_attempt_at) where state = 'pending'`.

### Постановка

Один запрос `insert into notifications (...) select ... on conflict do nothing` для всех подходящих периодов и получателей. Получатель общего чата - строка `group`, только если задан `TELEGRAM_CHAT_ID`. Вызывается тиком и `after_change`. Два параллельных тика дублей не дают: их не пускает `unique`.

Напоминание о просрочке ставится для любого неоплаченного просроченного периода действующего платежа, если его ещё не было: если система не работала в первый день просрочки или общий чат настроили позже, напоминание уходит при первом тике.

### Отправка

Одна строка - одна транзакция:

1. `select ... where state = 'pending' and next_attempt_at <= now() and recipient not in (<чаты на паузе>) order by next_attempt_at limit 1 for update skip locked`.
2. Повторная проверка теми же `due_soon` и `overdue_reminder`: оплаченный период, прекращённый платёж или прошедший срок у `due_soon` переводят строку в `cancelled`.
3. Отправка, затем запись итога и коммит.

Итоги: успех - `sent`, `sent_at`, `external_id`; временная ошибка (сеть, 5xx, 429, неверный токен) - `attempts + 1`, `next_attempt_at = now + min(60 * 2^(attempts-1), 3600)` секунд, для 429 - время из ответа; окончательная (чат не найден, бот удалён из чата, неверный запрос) - `failed`. Предела попыток нет: временная ошибка повторяется раз в час, пока напоминание актуально; устаревшее отменит проверка из шага 2.

`last_error` - не длиннее 500 символов, токен бота в нём заменяется на `***`.

Гарантия - "хотя бы один раз": повтор возможен, только если процесс упал между ответом Telegram и коммитом.

### Паузы по чатам

Отправитель помнит, когда каждому получателю можно писать снова: общему чату - через 3 секунды (20 сообщений в минуту), личному - через 1 секунду. Получатели на паузе исключаются из выборки, остальные не ждут. Паузы ведёт каждый экземпляр сам; лимит между экземплярами не согласуется, превышение даст 429 и повтор по времени из ответа.

### Telegram

`apps/reminders/telegram.py`: протокол `Notifier.send(chat_id, text) -> message_id` и ошибки `TemporaryDeliveryError(retry_after)`, `PermanentDeliveryError`, `ChatBlocked`. Реализация на aiogram: `AiohttpSession(proxy=TELEGRAM_PROXY_URL, timeout=10)`. Соответствие ошибок: `TelegramRetryAfter` - временная со временем; `TelegramForbiddenError` - `ChatBlocked`; `TelegramBadRequest`, `TelegramNotFound`, `TelegramMigrateToChat` - окончательная; остальные ошибки Telegram, сети и таймаут - временная. Тесты используют фейковый `Notifier`.

Текст без разметки, чтобы название платежа не требовало экранирования:

- `due_soon`: "Напоминание: до срока оплаты 3 дня. Аренда офиса - 150 000,00 RUB, срок 27.10.2026" (для срока сегодня - "срок оплаты сегодня");
- `overdue`: "Просрочена оплата: Аренда офиса - 150 000,00 RUB, срок был 23.10.2026".

### Настройки

`ReminderSettings` читают `api` и `worker`: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `TELEGRAM_PROXY_URL` (секрет: в адресе может быть пароль), `REMINDER_DAYS_BEFORE` (по умолчанию 3, от 0 до 30). Общий чат без токена - ошибка конфигурации. Без токена `worker` досоздаёт периоды и ставит напоминания, но не отправляет и пишет предупреждение.

### Задачи worker

- `scheduler`, раз в 60 секунд: досоздание периодов, постановка напоминаний, итог в журнал (`tick_done`).
- `reminder_sender`, раз в 2 секунды: отправляет всё, что можно отправить сейчас, и засыпает.

## Risks / Trade-offs

- Строка заблокирована, пока идёт запрос к Telegram (до 10 секунд): другие экземпляры её пропускают и берут следующие.
- Повтор сообщения при падении между отправкой и коммитом - осознанный выбор "хотя бы один раз".
