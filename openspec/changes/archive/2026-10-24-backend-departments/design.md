# Design

## Decisions

### Таблица и связь

`departments`: `id`, `name` (до 100 символов, `unique`), `created_at`. У `recurring_payments.department_id` появляется внешний ключ `on delete set null`: удаление отдела очищает ссылку у платежей в той же операции базы, отдельный код не нужен. Права от отделов не зависят (ADR-012).

Уникальность названия проверяет база; нарушение `unique` превращается в 409 `department_name_taken`. Сравнение с учётом регистра: "Офис" и "офис" - разные отделы. Проверка без учёта регистра потребовала бы индекса по `lower(name)`; для справочника из нескольких строк это лишнее.

### Связь модулей

`departments.service` даёт `payments` две функции, работающие в чужой сессии:

- `department_exists(session, id)` - проверка при создании и изменении платежа;
- `department_name(column)` - коррелированный подзапрос с названием отдела по колонке `department_id`. Его добавляют запросы `payments` (строки платежей и периодов, данные для напоминания), и название приходит тем же запросом без отдельного обращения.

`departments` не зависит от `payments`: удаление отдела не трогает таблицы платежей, ссылку очищает внешний ключ.

### Отдел в напоминании

Если у платежа есть отдел, в тексте после названия платежа в скобках стоит отдел: "Напоминание: до срока оплаты 3 дня. Аренда офиса (Офис) - 150 000,00 RUB, срок 27.10.2026".

### Журнал

`department.created`, `department.renamed` (старое и новое название), `department.deleted`.

### Список

Список отделов сортируется по названию, с пагинацией как у остальных списков.
