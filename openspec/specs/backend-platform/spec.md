# backend-platform Specification

## Purpose
Общее поведение процессов backend, на которое опираются все модули и эксплуатация: проверки живости и готовности, документация API, формат ошибок, проверка конфигурации, журнал, "сегодня" в часовом поясе системы, остановка `worker` и миграции.

## Requirements

### Requirement: Проверка живости
Процесс `api` SHALL отвечать на `GET /healthz` кодом 200, пока процесс работает, без обращения к базе и без авторизации.

#### Scenario: Процесс работает
- **WHEN** клиент запрашивает `GET /healthz`
- **THEN** ответ 200

#### Scenario: База недоступна
- **WHEN** PostgreSQL недоступна и клиент запрашивает `GET /healthz`
- **THEN** ответ 200

### Requirement: Префикс API и документация
Эндпоинты API SHALL жить под префиксом `/api/v1`. Swagger SHALL открываться на `/api/v1/docs`, а схема OpenAPI - на `/api/v1/openapi.json`. Проверки `/healthz` и `/readyz` в схему API не входят.

#### Scenario: Swagger доступен
- **WHEN** клиент открывает `/api/v1/docs`
- **THEN** ответ 200 со страницей Swagger, которая загружает `/api/v1/openapi.json`

#### Scenario: Проверки не в схеме
- **WHEN** клиент запрашивает `/api/v1/openapi.json`
- **THEN** в схеме нет путей `/healthz` и `/readyz`

### Requirement: Единый формат ошибок
Любой ответ с ошибкой SHALL быть JSON в формате Aéza v2 (ADR-015): `statusCode` (код HTTP), `message` (понятный человеку текст на русском), `error` (машинный код на английском, по нему ветвится клиент), `timestamp` (момент ошибки, ISO 8601), `path` (путь запроса), `payload` (подробности: список `{field, message}` для ошибок полей, `{entity, id}` для "не найдено", иначе текст ошибки) и `requestId` (совпадает с заголовком `X-Request-ID`).

#### Scenario: Неизвестный путь
- **WHEN** клиент запрашивает несуществующий путь под `/api/v1`
- **THEN** ответ 404 в общем формате ошибок с `error` `not_found`

#### Scenario: Ошибка проверки данных
- **WHEN** тело или параметры запроса не проходят проверку
- **THEN** ответ 400 с `error` `bad_request`, `payload` называет каждое неверное поле в camelCase и объясняет ошибку на русском, например "Должно быть целым числом" или "Не меньше 1"

#### Scenario: Непредвиденная ошибка
- **WHEN** при обработке запроса происходит непредвиденная ошибка
- **THEN** ответ 500 в общем формате без трассировки, текста исключения и внутренних данных
- **AND** ошибка с трассировкой записана в журнал

### Requirement: Проверка конфигурации при старте
Процессы `api`, `worker` и применение миграций SHALL не запускаться, если обязательная переменная окружения отсутствует или имеет неверный формат; сообщение SHALL называть каждую такую переменную и не показывать значения секретов.

#### Scenario: Не задана обязательная переменная
- **WHEN** процесс запускается без `DATABASE_URL`
- **THEN** процесс завершается с ненулевым кодом, сообщение называет `DATABASE_URL`

#### Scenario: Неверный часовой пояс
- **WHEN** `TZ` не является именем часового пояса IANA
- **THEN** процесс не запускается, сообщение называет `TZ`

#### Scenario: Секрет не попадает в сообщение
- **WHEN** запуск не удался из-за другой переменной, а секреты заданы
- **THEN** значения секретов отсутствуют в выводе процесса

### Requirement: Идентификатор запроса
Каждый ответ `api` SHALL содержать заголовок `X-Request-ID`. Если клиент прислал корректный `X-Request-ID`, он SHALL использоваться; иначе создаётся новый. Все записи журнала по запросу SHALL содержать этот идентификатор.

#### Scenario: Клиент не прислал идентификатор
- **WHEN** запрос пришёл без `X-Request-ID`
- **THEN** ответ содержит новый непустой `X-Request-ID`

#### Scenario: Клиент прислал идентификатор
- **WHEN** запрос пришёл с корректным `X-Request-ID`
- **THEN** ответ содержит тот же `X-Request-ID`, и записи журнала по запросу содержат его

#### Scenario: Некорректный идентификатор
- **WHEN** присланный `X-Request-ID` пустой, слишком длинный или содержит недопустимые символы
- **THEN** он не используется, ответ содержит новый идентификатор

### Requirement: Журнал без секретов
Процессы backend SHALL писать журнал в стандартный вывод по одной записи JSON на строку с полями времени, уровня, процесса и сообщения. Пароли, токены и секреты SHALL не попадать в журнал.

#### Scenario: Запись журнала
- **WHEN** `api` обработал запрос
- **THEN** в стандартном выводе есть запись JSON с временем, уровнем, именем процесса, сообщением и `request_id`

#### Scenario: Секрет в заголовке
- **WHEN** запрос пришёл с заголовком `Authorization`
- **THEN** значение заголовка отсутствует в журнале

### Requirement: Сегодняшняя дата системы
"Сегодня" для правил сроков SHALL считаться как текущая дата в часовом поясе `TZ`. Переменная `CLOCK_TODAY` SHALL подменять "сегодня" для демо и ручных проверок вне продакшена; при `APP_ENV=production` с заданной `CLOCK_TODAY` процессы SHALL не запускаться.

#### Scenario: Граница суток
- **WHEN** в UTC ещё 23 октября 22:30, а `TZ` равен `Europe/Moscow`
- **THEN** "сегодня" равно 24 октября

#### Scenario: Подмена даты для демо
- **WHEN** `CLOCK_TODAY=2026-11-30` и `APP_ENV` не `production`
- **THEN** "сегодня" равно 30 ноября 2026

#### Scenario: Подмена даты в продакшене
- **WHEN** `CLOCK_TODAY` задана и `APP_ENV=production`
- **THEN** процесс не запускается, сообщение называет `CLOCK_TODAY`

### Requirement: Корректная остановка worker
Процесс `worker` SHALL по сигналу остановки (SIGTERM, SIGINT) перестать начинать новую работу, дождаться завершения текущей не дольше `SHUTDOWN_TIMEOUT` (по умолчанию 15 секунд) и завершиться с кодом 0.

#### Scenario: Остановка без текущей работы
- **WHEN** `worker` простаивает и получает сигнал остановки
- **THEN** процесс завершается с кодом 0

#### Scenario: Остановка во время работы
- **WHEN** `worker` выполняет задачу и получает сигнал остановки
- **THEN** новая задача не начинается, текущая завершается, затем процесс завершается с кодом 0

#### Scenario: Задача не укладывается в срок
- **WHEN** текущая задача не завершилась за `SHUTDOWN_TIMEOUT`
- **THEN** задача прерывается, в журнал пишется предупреждение, процесс завершается

### Requirement: Применение миграций
Применение миграций SHALL приводить пустую базу к последней версии схемы, а повторное применение к уже обновлённой базе SHALL ничего не менять и завершаться успешно.

#### Scenario: Пустая база
- **WHEN** миграции применяются к пустой базе
- **THEN** команда завершается успешно, `/readyz` после этого отвечает 200

#### Scenario: Повторное применение
- **WHEN** миграции применяются второй раз
- **THEN** команда завершается успешно и схема не меняется

### Requirement: Готовность api
Процесс `api` SHALL отвечать на `GET /readyz` кодом 200, только если база доступна и к ней применены все миграции; иначе 503 с причиной в теле в общем формате ошибок. API Aéza в проверку готовности не входит: без него не работает только вход. Авторизация не требуется.

#### Scenario: Всё готово
- **WHEN** база доступна, миграции применены, клиент запрашивает `GET /readyz`
- **THEN** ответ 200

#### Scenario: База недоступна
- **WHEN** PostgreSQL недоступна и клиент запрашивает `GET /readyz`
- **THEN** ответ 503 с кодом ошибки, который называет недоступную базу

#### Scenario: Миграции не применены
- **WHEN** база доступна, но в ней нет последней миграции
- **THEN** ответ 503 с кодом ошибки, который называет неприменённые миграции

#### Scenario: Aéza недоступна
- **WHEN** база готова, а API Aéza не отвечает
- **THEN** ответ 200

### Requirement: Оформление документации
Swagger на `/api/v1/docs` SHALL открываться в тёмной теме веб-панели со вступлением о входе, ролях, формате и ошибках, с описанием каждого раздела и операции. Авторизация SHALL сохраняться между перезагрузками страницы, у входных схем SHALL быть рабочие примеры для "Try it out".

#### Scenario: Открыть документацию
- **WHEN** разработчик открывает `/api/v1/docs`
- **THEN** страница "Незабудка API" в тёмной теме, разделы свёрнуты, кнопка Authorize сохраняет токен
